# Repository Guidelines

## Project Structure & Module Organization

- `TavoloFlow.slnx` groups the backend projects; `global.json` specifies the .NET SDK.
- `backend/TavoloFlow.Api/` contains the ASP.NET Core 10 controller-based API. Startup lives in `Program.cs`; `Entities/` contains the nine persistence entities, and `Data/` contains `ApplicationDbContext`, EF Core mappings and migrations, and catalog deletion services. `Accounts/` implements development account initialization, store authentication and authorization; `Controllers/AuthController.cs` exposes the account endpoints. `Menus/` implements menu maintenance, availability, language rules and anonymous menu reading; `Tables/` implements table maintenance. `Dining/` implements opening tables, the shared session bill summary (`BillSummaryResponse`), encrypted join codes and the entrance rule; `Guests/` implements guest authentication, access checks and join rate limits. The corresponding controllers expose store and public APIs separately. `Ordering/` implements idempotent guest ordering, immutable snapshots and cursor-paged table orders; `Dining/` also owns the accepting-orders switch. `Kitchen/` implements the staff queue, conditional READY/cancellation transitions and transactionally updated bill versions. `Billing/` implements active bills, all three closures (PAID/VOIDED/EMPTY) and owner-only closed history; the system records confirmation of offline payment, not payment transactions.
- `backend/TavoloFlow.Api.Tests/` contains data-layer, account, menu, table, public-menu, dining, guest, ordering, kitchen and billing integration tests using disposable PostgreSQL containers and `WebApplicationFactory`.
- `frontend/src/` contains the React/TypeScript application. `routes/` defines TanStack file-based routes; `router.tsx` creates the router from the generated `routeTree.gen.ts`. Account pages and identity queries live in `features/accounts/`; menu maintenance lives in `features/menu/`, table maintenance and QR generation in `features/tables/`, and anonymous guest browsing in `features/public-menu/`. `features/dining/` provides `/staff/floor`; `features/guests/` manages guest verification and visit lifecycle on the public menu; `features/orders/` provides tab-local carts, order confirmation, table orders and durable unknown-result recovery within `/q/{token}`. `features/kitchen/` provides `/staff/kitchen`, paged queue polling, cancellation confirmation, GET-only recovery and opt-in audio. `features/billing/` provides `/staff/orders`, `/staff/history`, shared floor bill/zero-closure panels and GET-only closure recovery. Shared HTTP/CSRF/error handling lives in `lib/api.ts`; shared shadcn UI lives in `components/ui/`, utilities in `lib/`, and theme variables in `index.css`.
- `docs/` contains product requirements and the DBML schema. Root `compose.yaml` defines local PostgreSQL.

## Build, Test, and Development Commands

Run backend and infrastructure commands from the repository root:

- `cp .env.example .env`: initialize local database settings; replace the password before starting PostgreSQL.
- `docker compose up -d db`: start PostgreSQL on localhost port 5432.
- `dotnet build TavoloFlow.slnx`: restore dependencies and build the backend solution.
- `dotnet run --project backend/TavoloFlow.Api --launch-profile https`: start the API at `https://localhost:7298`.
- `dotnet run --project backend/TavoloFlow.Api --launch-profile http`: start the API at `http://localhost:5093` for the Vite `/api` proxy.
- `dotnet run --project backend/TavoloFlow.Api --launch-profile http -- --seed-dev-accounts`: explicitly initialize Development accounts after configuring `DevelopmentSeed` and applying migrations; see `docs/store-accounts.md`.
- `dotnet test TavoloFlow.slnx`: run backend tests.

From `frontend/`, run `npm install` to install dependencies, `npm run dev` for development, `npm run build` for TypeScript checking and production output, `npm run lint` for Oxlint, `npm run format` (or `npm run format:check`) for Prettier, and `npm run preview` to preview the build.

The build runs `vite build && tsc -b`: Vite generates the route tree before TypeScript checks route types. Commit `src/routeTree.gen.ts` with route changes; never edit it manually. It is excluded from lint. The TanStack Router Vite plugin must precede the React plugin and enables automatic route code splitting.

## Coding Style & Naming Conventions

Use four-space indentation in C# and two spaces in TypeScript/TSX. Use PascalCase for C# types/methods and React components; use camelCase for JavaScript functions and variables. Prefer file-scoped C# namespaces and preserve nullable annotations. Use `@/` imports for frontend source paths. Frontend files are formatted with Prettier (`frontend/.prettierrc.json`, print width 100); run `npm run format` before committing. C# has no formatter configured, so match the surrounding style. Oxlint checks React hooks and TypeScript rules.

Keep route files thin: URL/search configuration belongs in `routes/`, while forms and feature state belong in the corresponding `features/` directory. `AuthBoundary` observes the shared identity query; do not duplicate authentication requests in route loaders. Public menu routes do not use `AuthBoundary` or request `/me`. The store layout sets available width, and pages choose their own card width. Menu/table editing keeps its local form snapshot during background refresh; private query keys include restaurant and account IDs. Public queries use the `public` prefix and survive account changes; `publicRequest` omits credentials and store-auth failure handling. Writes have no automatic retry or offline queue. Add UI components using the existing shadcn configuration (Base UI, `base-nova`, `neutral`); use semantic theme colors and preserve labels, focus styles, and at least 44px account form controls. Navigation uses TanStack `Link` with `buttonVariants` from `components/ui/button-variants.ts`; keep style utilities separate from component exports for Fast Refresh. The `Route` export lint exception applies only to route files.

## Testing Guidelines

Backend tests use xUnit, Coverlet, and Testcontainers.PostgreSql. The existing integration tests require Docker and apply real migrations to a disposable PostgreSQL database, separate from the development database. Write meaningful assertions; name new classes `<Subject>Tests` and methods `Method_Scenario_ExpectedResult`. Collect coverage with `dotnet test TavoloFlow.slnx --collect:"XPlat Code Coverage"`; no minimum threshold is configured. No frontend test framework is installed. With Node 24, run `node --test --test-isolation=none tests/*.test.ts` from `frontend/` for pure language, QR URL, query-scope, dining recovery, cart/order recovery, kitchen synchronization and billing confirmation/recovery logic; also run build/lint and manually verify affected UI flows.

## Commit & Pull Request Guidelines

History uses short, scoped messages such as `backend: docker postgresql setup` and `docs: er-diagram`; follow that pattern. PRs should describe behavior changes, link relevant issues, and record validation commands/results. Include screenshots for visible UI changes and configuration or schema notes where relevant.

## Security & Configuration

Keep credentials in ignored `.env` files, environment variables, or .NET user secrets. Commit only safe example values. Docker Compose settings do not automatically configure the API connection string. Store authentication uses an HttpOnly session cookie with a fixed 16-hour ticket and CSRF validation on controller writes. Use `CurrentAccount` for trusted restaurant identity and the store authorization policies for business endpoints; only self-account operations may bypass the first-password-change requirement. Data Protection keys must stay outside Git and persist across deployments.

## Menu Rules

Menu content and availability writes derive the restaurant from `CurrentAccount` and lock its restaurant row before category/item rows. Default language is a stable OWNER preference (`zh`/`it`/`en`), updated only through its setting endpoint, even on empty menus; content changes never repair or replace it. Reads use a repeatable-read snapshot and derive read-only `availableLanguages` from loaded names. General name fallback is default → Italian → Chinese → English, deduplicated; the staff UI explicitly selects Chinese before this chain. Descriptions follow the resolved name language. Item content DTOs exclude availability; the dedicated availability endpoint updates only that field. Every item content save requires allergen review, even when sold out. Keep price inputs in decimal strings and send integer cents within JavaScript’s safe range. `CatalogDeletionService.DeleteMenuItemAsync` always owns its transaction and locks the restaurant before the item; do not wrap it in an outer transaction. Table deletion also owns its transaction. Preserve historical order snapshots. See `docs/menu-management.md` for contracts and learning exercises.

## Tables and Public Menu Rules

Table labels are trimmed, 1–50 characters, and unique per restaurant with case-sensitive comparison. Rename and enabled-state writes update only their own field under the table row lock. QR tokens are server-generated random 32-byte Base64URL values and remain fixed until physical deletion; no rotation endpoint exists. Reuse the deletion service without an outer transaction; active sessions prevent deletion, while closed sessions retain snapshots with a null table link. Public bootstrap resolves ownership only from the QR token and reads entrance plus menu in one Repeatable Read transaction; `MenuReader` does not start its own transaction. It exposes no join codes, orders or account information and creates no sessions. Suspended restaurants and disabled tables still expose their menu with an explanatory status. Guest UI always offers zh/it/en, remembers explicit choices per restaurant, and otherwise uses the owner's preference. A confirmed invalid QR replaces cached menu data; network failures keep earlier data with a warning. QR PNGs are generated locally with `qrcode`; optional `VITE_PUBLIC_BASE_URL` must be an HTTP(S) origin. See `docs/tables-public-menu.md` for contracts, LAN setup and learning exercises.

## Dining and Guest Access Rules

Opening acquires restaurant SHARE then table UPDATE locks; guest joining/code reading acquires restaurant, table and session SHARE locks in that order. EMPTY closure shares `BillingService`'s closure path with PAID/VOIDED: it owns a transaction and takes the same session UPDATE lock ordering, kitchen transitions and checkout use. It requires confirmed version, zero amount, guests-left confirmation and no orders of any status; it clears the code ciphertext without incrementing BillVersion. Never reopen a closed session. Join codes use purpose-bound Data Protection, not plaintext or password hashes.

The Browser authentication selector routes `/api/public/*` to Guest and other requests to Store. Guest cookies are HttpOnly, scoped to `/api/public`, with fixed 12-hour tickets; each protected operation validates the bound session against current database state. Guest and store CSRF tokens are fetched from their respective endpoints and must use the matching identity. `publicRequest` remains anonymous; `guestRequest/guestWrite` carry credentials without store-auth failure handling. Guest query keys use `guest` plus restaurant/table/session IDs, survive store identity changes and are cleared on guest invalidation; never persist code values or tickets. Automatic recovery of unknown writes uses GET only. Ordering alone permits an explicit manual retry with the original persisted request ID and body; never automatically resend POST. Guest code displays discard late responses on lifecycle/visibility changes. See `docs/dining-guest-access.md` for contracts, state gates, testing and development activation.

## Cart and Ordering Rules

Order creation derives the restaurant/table/session from `GuestIdentity` and locks restaurant SHARE → table SHARE → session UPDATE. Validate ACTIVE and binding, then return an existing `(session_id, client_request_id)` order before applying first-submission input, service, availability or price gates. Menu writers take restaurant UPDATE; keep this coordination so snapshots and price checks cannot race. Save the whole order and increment BillVersion once in one transaction. Read orders while holding session SHARE; active authorized guests can read during service/table/ordering pauses. Never expose client request IDs in order DTOs. Pagination uses `(created_at, id)` descending, default 50/max 100; totals exclude cancelled orders. Keep the nine-table schema unchanged.

Carts are isolated by tab and restaurant/table, retaining the observed session (null before opening). Explicitly confirm the first opened visit; never migrate an old visit's draft. Limit 30 lines, 1–20 per line, 100 portions, 200-character remarks and 500-character order notes; protect line/order/accumulated bill totals against JavaScript safe-integer overflow. Use secure `getRandomValues` UUIDv4 for HTTP LAN support. Persist and read back the full intent before POST; blocked storage permits editing but prevents submission. Pending intents freeze edits. Automatic recovery revalidates access then queries the original ID; 404 is only “not found yet”. Manual retries use identical ID/content and fresh CSRF. A rejection after an unknown result does not release the intent. Reauthentication keeps local intent but hides/removes protected responses; confirmed closure clears the visit and directs unknown results to staff. Cancel requests and discard late responses on identity/lifecycle changes. See `docs/cart-ordering.md` for the four implementation steps, experiments and validation.

## Kitchen and Cancellation Rules

Kitchen queries derive restaurant/role from `CurrentAccount`. Lists include only ACTIVE sessions: NEW sorts by creation time/ID ascending; READY and CANCELLED sort by their transition time/ID descending. Cursor scope includes restaurant and status. Read list rows and counters in one Repeatable Read snapshot. `createdOrderCount` includes all existing restaurant orders, including cancelled and closed visits; it detects new submissions beyond the visible page and is not an audit sequence. Reassess it if historical purging is introduced.

Ready and cancel resolve the tenant-scoped order, then acquire only its session UPDATE lock; never acquire restaurant/table locks afterwards. Re-read state and execute a conditional UPDATE. Cancellation requires `expectedStatus` NEW/READY and a trimmed 1–500-character reason; READY cancellation is OWNER-only. Preserve snapshots, original amount and any ready timestamp. Increment BillVersion exactly once with cancellation in the same transaction; READY does not increment. Repeated or mismatched transitions return ORDER_CHANGED; CLOSED sessions reject writes. Paused service/table/ordering does not block existing work. Do not add cancellation actor fields or permit EMPTY for fully cancelled visits.

Kitchen polls every 10 seconds only while visible/online and refreshes all loaded pages. A stale (30-second) or failed view blocks writes. Audio starts only after a user gesture; first load, enable, view change, foreground resume and reconnect establish a silent baseline. Persist only minimal pending action identifiers per tab/restaurant/account; recovery is GET-only and fresh writes require human confirmation. Cancel late work on lifecycle/identity changes. See `docs/kitchen-cancellation.md` for contracts and learning experiments.

## Billing and History Rules

Active bills are STAFF/OWNER readable; PAID closure and full closed history require OWNER. Bill reads hold session SHARE; PAID/VOIDED closure holds only session UPDATE and never takes restaurant/table row locks afterwards. Recompute amount, counts and version inside the transaction. PAID requires positive receivables and no NEW; VOIDED requires existing orders all CANCELLED, zero total and guests-left confirmation. EMPTY remains limited to no orders of any status. Paused entrances do not prevent closure. Persist CLOSED, reason, total, closing time and null code ciphertext atomically without incrementing BillVersion. Identical closure type/version/amount on an already closed session returns its stored result; mismatches cannot rewrite it. Clamp closing time to the latest business timestamp.

Bill orders page ascending by creation time/ID, default 50/max 100; cursors bind tenant, session, active/history mode and bill version. BILL_CHANGED returns currentBill and resets loaded bill pages. History uses stored snapshots/closed totals, exact trimmed case-sensitive historical table labels and closure reasons. Default dates are the restaurant's local today; explicit dates are a paired inclusive range converted to UTC boundaries with DST. History sorts closed time/ID descending; cursors bind tenant and resolved filters, retaining date bounds across midnight.

Keep selected session IDs in URL search. Freeze confirmation version/amount; polling must not silently replace them. Active bill polling is 30 seconds while visible/online; stale, failed and resumed-but-not-refreshed views cannot close. Persist only session ID/closure kind per tab/account/restaurant; unknown closures recover by GET of the original session, never automatic POST. Clear protected guest state through existing lifecycle checks and invalidate affected private queries after closure. See `docs/billing-history.md` for contracts, experiments and validation.

## Platform Administration and Pilot Operations

`Platform/` owns the independent Platform cookie, bootstrap/recovery CLI and restaurant/account management. Browser selects Platform for `/api/platform`, Guest for `/api/public`, Store otherwise. Platform has a fixed 8-hour ticket and its own limiter; every request verifies active state and credential version. CSRF additional data binds all tokens, including anonymous tokens, to the three scopes. Platform does not grant store business permissions. Use `CurrentPlatformAccount` only for platform administration and `CurrentAccount` for OWNER staff maintenance.

Create the client-selected restaurant UUID and both store accounts atomically: SUSPENDED, ordering off, EUR/Europe/Rome, first password change required. Generated temporary passwords appear only in the successful create/reset response. Expected target credential versions protect reset/active writes; use ACCOUNT_CHANGED for target conflicts, never the current-user credential error. Suspend locks the restaurant and closes ordering; enabling ordering checks ACTIVE under that same lock. Restoring ACTIVE does not enable ordering.

Frontend `features/platform/` uses separate identity, request/CSRF functions and `platform` query keys; `/staff/settings` is OWNER-only. Use direct promises for secret-bearing writes; never cache or persist temporary passwords. Cancel late work and clear secret displays on navigation, identity and visibility changes. Persist only scoped pending identifiers/expected versions before writes. Recover through GET; create retries need explicit confirmation and the original UUID. Reset recovery compares versions but cannot recover a lost password or prove which administrator changed it. Other identities' caches and pending markers must survive unrelated login/logout.

`deploy/` is separate from development Compose: Caddy only publishes ports, API UID 1654, separate runtime/migration database credentials, explicit EF bundle, persistent keys and certificates. Production requires an absolute writable key directory. Trust only configured proxy IPs; reserve the proxy outside Docker's dynamic address pool. Health responses remain minimal and no-store. Never add automatic startup migrations or log passwords, tickets, join codes or request bodies.

Run `npm run test:e2e` only with `PILOT_ISOLATED=1`, a localhost `PILOT_BASE_URL`, and `PILOT_ADMIN_PASSWORD_FILE`; tests create fixture restaurants and leave one active session for the restore drill. Playwright traces/videos/failure screenshots are disabled to avoid recording secrets; capture only explicitly safe screens. Backend regressions require Docker. Backup/restore tools protect files, include the key ring and refuse existing restore targets. Restore suspends service and advances Store/Platform credential versions; Guest authorization and active bills still require offline reconciliation. See `docs/platform-pilot.md`, `deploy/README.md` and `docs/pilot-operations.md` for commands and recorded evidence.
