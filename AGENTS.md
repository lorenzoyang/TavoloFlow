# Repository Guidelines

## Project Structure & Module Organization

- `TavoloFlow.slnx` groups the backend projects; `global.json` specifies the .NET SDK.
- `backend/TavoloFlow.Api/` contains the ASP.NET Core 10 controller-based API. Startup lives in `Program.cs`; `Entities/` contains ten persistence entities, and `Data/` contains `ApplicationDbContext`, EF Core mappings and migrations, the row-lock helpers (`RowLocks`) and catalog deletion services. `Common/` holds cross-cutting code: the `ApiError` envelope with `ApiException` and its global filter, browser identity selection and CSRF scoping (`BrowserSecurity`), keyset paging, enum text, input rules and the fixed-window rate limiter. `Accounts/` implements development account initialization, store authentication and authorization; `Controllers/AuthController.cs` exposes the account endpoints. `Menus/` implements menu maintenance, availability, language rules and anonymous menu reading; `Tables/` implements table maintenance. `Dining/` implements opening tables, the shared session bill summary (`BillSummaryResponse`), encrypted join codes and the entrance rule; `Guests/` implements guest authentication, access checks and join rate limits. The corresponding controllers expose store and public APIs separately. `Ordering/` implements idempotent guest ordering, immutable snapshots and cursor-paged table orders; `Dining/` also owns the accepting-orders switch. `Kitchen/` implements the staff queue, conditional item READY/cancellation transitions and transactionally updated bill versions. `Billing/` implements active bills, all three closures (PAID/VOIDED/EMPTY) and owner-only closed history; the system records confirmation of offline payment, not payment transactions. `Platform/SubscriptionService` owns restaurant service periods and offline annual fee collection.
- `backend/TavoloFlow.Api.Tests/` contains data-layer, account, menu, table, public-menu, dining, guest, ordering, kitchen and billing integration tests using disposable PostgreSQL containers and `WebApplicationFactory`.
- `frontend/src/` contains the React/TypeScript application. `routes/` defines TanStack file-based routes; `router.tsx` creates the router from the generated `routeTree.gen.ts`. Account pages, identity queries and the installable staff app hook live in `features/accounts/`; menu maintenance lives in `features/menu/`, table maintenance and QR generation in `features/tables/`, and anonymous guest browsing in `features/public-menu/`. `features/dining/` provides `/staff/floor`; `features/guests/` manages guest verification and visit lifecycle on the public menu; `features/orders/` provides tab-local carts, order confirmation, table orders and durable unknown-result recovery within `/q/{token}`. `features/kitchen/` provides `/staff/kitchen`, paged queue polling, cancellation confirmation, GET-only recovery and opt-in audio. `features/billing/` provides `/staff/orders`, `/staff/history`, shared floor bill/zero-closure panels and GET-only closure recovery. Shared HTTP/CSRF/error handling lives in `lib/api.ts`; shared shadcn UI lives in `components/ui/`, app-wide composites (page header, notices, confirmation dialog, list/detail layout, filter chips, loading/empty states, brand mark) in `components/`, utilities in `lib/`, and the theme tokens in `index.css`. `features/accounts/navigation.ts` lists the store navigation. `frontend/public/` holds the favicon, the staff PWA manifest, the service worker and the app icons.
- `docs/` contains product requirements, the DBML schema, and the Chinese deployment guide and maintainer notes in `docs/zh-CN/` (`deployment-guide.md`, `deployment-notes.md`). Root `compose.yaml` defines local PostgreSQL. `deploy/` contains the separate production Compose, Docker builds, Caddy configuration and explicit release/backup/recovery commands; see `docs/deployment-validation.md` for verification.
- Production business routes and `/api` share `https://app.qiaotavoloflow.it` on the netcup VPS. The apex domain and `www` are reserved for an independently maintained Astro marketing site in another repository on Cloudflare. This repository must not serve those marketing hosts or add parent-domain cookies/CORS to connect the two sites.

## Build, Test, and Development Commands

Run backend and infrastructure commands from the repository root:

- `cp .env.example .env`: initialize local database settings; replace the password before starting PostgreSQL.
- `docker compose up -d db`: start PostgreSQL on localhost port 5432.
- `dotnet build TavoloFlow.slnx`: restore dependencies and build the backend solution.
- `dotnet run --project backend/TavoloFlow.Api --launch-profile https`: start the API at `https://localhost:7298`.
- `dotnet run --project backend/TavoloFlow.Api --launch-profile http`: start the API at `http://localhost:5093` for the Vite `/api` proxy.
- `dotnet run --project backend/TavoloFlow.Api --launch-profile http -- --seed-dev-accounts`: explicitly initialize Development accounts after configuring `DevelopmentSeed` and applying migrations; see `docs/store-accounts.md`.
- `dotnet test TavoloFlow.slnx`: run backend tests.

From `frontend/`, run `npm install` to install dependencies, `npm run dev` for development, `npm run build` for TypeScript checking and production output, `npm run lint` for Oxlint, `npm run format` (or `npm run format:check`) for Prettier, and `npm run preview` to preview the build.

The build runs `vite build && tsc -b`: Vite generates the route tree before TypeScript checks route types. Commit `src/routeTree.gen.ts` with route changes; never edit it manually. It is excluded from lint. The TanStack Router Vite plugin must precede the React plugin and enables automatic route code splitting.

## Coding Style & Naming Conventions

Use four-space indentation in C# and two spaces in TypeScript/TSX. Use PascalCase for C# types/methods and React components; use camelCase for JavaScript functions and variables. Prefer file-scoped C# namespaces and preserve nullable annotations. Use `@/` imports for frontend source paths. Frontend files are formatted with Prettier (`frontend/.prettierrc.json`, print width 100); run `npm run format` before committing. C# has no formatter configured, so match the surrounding style. Oxlint checks React hooks and TypeScript rules.

Keep route files thin: URL/search configuration belongs in `routes/`, while forms and feature state belong in the corresponding `features/` directory. `AuthBoundary` observes the shared identity query; do not duplicate authentication requests in route loaders. Public menu routes do not use `AuthBoundary` or request `/me`. The store layout sets available width, and pages choose their own card width. Menu/table editing keeps its local form snapshot during background refresh; private query keys include restaurant and account IDs. Public queries use the `public` prefix and survive account changes; `publicRequest` omits credentials and store-auth failure handling. Writes have no automatic retry or offline queue. Add UI components with the existing shadcn CLI configuration (Base UI, `base-nova`) and answer “no” when it offers to overwrite `button.tsx`: style utilities stay separate from component exports for Fast Refresh (`button-variants.ts`, `toggle-variants.ts`). Links styled as buttons use TanStack `Link` with `buttonVariants`, which merges conflicting classes exactly as `Button` does. Preserve labels and focus styles, and follow the UI conventions below. The `Route` export lint exception applies only to route files.

## UI Conventions

The visual system is a warm trattoria: cream surfaces and terracotta actions, defined as semantic tokens in `index.css`; components use tokens and variants, never raw colours. Each colour has one meaning everywhere: `warning` (saffron) is waiting, new or due soon; `success` (basil) is ready, available or paid; `destructive` (tomato) is cancel, void or delete; muted is cancelled or disabled. Guests see NEW as a neutral “received”, not a warning. V1 has no dark theme; keep the class-based `dark` variant so component `dark:` styles never follow the OS. Text is Geist with the platform CJK font; `font-display` (Fraunces) is only for the brand wordmark, the guest menu's restaurant and category names and printed table cards.

Base controls are touch-sized: buttons, inputs, selects, tabs and toggles reach 44px and checkboxes/switches have 44px hit areas, so call sites never add heights. Design mobile first. Phones show the store tabs as a bottom bar and tablets/desktops (≥md) as a side rail; both render `staffNavItems(role)`, and less frequent pages are reached from 首页 (`staffManagementItems`). Pages outside the tabs show a `PageHeader` back link, because an installed web app has no browser back button on iOS. Use `min-h-dvh`; fixed bars use `pt-safe`/`pb-safe` or `env(safe-area-inset-*)`.

Compose pages from `src/components/`: `PageHeader`; `Notice` for all inline feedback (errors are `role=alert`, other tones `role=status`); `ConfirmDialog` for the human confirmation in front of irreversible or money-related store writes (open a table, close a bill, cancel an order, delete, reset a password); `MasterDetail` for a list and its selected record, a non-modal column at ≥lg (`WIDE_SCREEN` in `lib/useMediaQuery.ts`) and a full-height sheet below, selected through the route's `sessionId` search where it has one; and `FilterChips`, `LoadingState`, `EmptyState`, `BrandMark`. Wide screens never use a modal for a detail view: Base UI modals mark the rest of the page `aria-hidden`. The guest page renders `CartPanel` once: a sticky column at ≥lg, otherwise a bottom sheet opened from `CartBar`.

Platform confirmations stay inline regions (`管理操作确认`, `收费操作确认`); creating a restaurant together with its first period still uses `window.confirm` (platform administrators only). The staff area is an installable PWA (`docs/pwa.md`); the platform stays a website and push notifications are not implemented. Only `StaffLayout` links `/staff.webmanifest` and, in production builds, registers `/sw.js` with scope `/staff` (`features/accounts/useInstallApp.ts`). Never link a manifest from `index.html`, guest or platform pages, so guests on `/q/*` are never offered an installation. The manifest id, start_url and scope stay `/staff` without a trailing slash, because the router drops trailing slashes and `/staff` must stay inside the app. The worker handles navigations only, network first with a built-in offline page, and uses no Cache Storage: never cache `/api`, pages or assets. The home page offers Chromium's install prompt, or per-device steps elsewhere. iOS uses the opaque `apple-touch-icon.png`. The kitchen's sound and keep-screen-on switches (`features/kitchen/audio.ts`, `lib/useWakeLock.ts`) store only device preferences in `localStorage`.

## Testing Guidelines

Backend tests use xUnit, Coverlet, and Testcontainers.PostgreSql. The existing integration tests require Docker and apply real migrations to a disposable PostgreSQL database, separate from the development database. Write meaningful assertions; name new classes `<Subject>Tests` and methods `Method_Scenario_ExpectedResult`. Collect coverage with `dotnet test TavoloFlow.slnx --collect:"XPlat Code Coverage"`; no minimum threshold is configured. No frontend test framework is installed. With Node 24, run `node --test --test-isolation=none tests/*.test.ts` from `frontend/` for pure language, QR URL, query-scope, dining recovery, cart/order recovery, kitchen synchronization and billing confirmation/recovery logic, plus the PWA manifest/icon invariants; also run build/lint and manually verify affected UI flows.

## Commit & Pull Request Guidelines

History uses short, scoped messages such as `backend: docker postgresql setup` and `docs: er-diagram`; follow that pattern. PRs should describe behavior changes, link relevant issues, and record validation commands/results. Include screenshots for visible UI changes and configuration or schema notes where relevant.

## Security & Configuration

Keep credentials in ignored `.env` files, environment variables, or .NET user secrets. Commit only safe example values. Docker Compose settings do not automatically configure the API connection string. Store authentication uses an HttpOnly persistent cookie with a fixed 30-day ticket, no sliding renewal and CSRF validation on controller writes. Store and Platform passwords accept 6–128 characters, including six digits, and cannot be entirely whitespace. Use `CurrentAccount` for trusted restaurant identity and the store authorization policies for business endpoints; only self-account operations may bypass the first-password-change requirement. Data Protection keys must stay outside Git and persist across restarts. Never add automatic startup migrations or log passwords, tickets, join codes or request bodies. Production templates live in `deploy/`; never merge them with the local database Compose. Production uses a trusted Caddy proxy, persistent Data Protection keys and explicit migration bundles. Never expose database/API container ports or apply migrations automatically at startup.

## Menu Rules

Menu content and availability writes derive the restaurant from `CurrentAccount` and lock its restaurant row before category/item rows. Default language is a stable OWNER preference (`zh`/`it`/`en`), updated only through its setting endpoint, even on empty menus; content changes never repair or replace it. Reads use a repeatable-read snapshot and derive read-only `availableLanguages` from loaded names. General name fallback is default → Italian → Chinese → English, deduplicated; the staff UI explicitly selects Chinese before this chain. Descriptions follow the resolved name language. Item content DTOs exclude availability; the dedicated availability endpoint updates only that field. Every item content save requires allergen review, even when sold out. Keep price inputs in decimal strings and send integer cents within JavaScript’s safe range. `CatalogDeletionService.DeleteMenuItemAsync` always owns its transaction and locks the restaurant before the item; do not wrap it in an outer transaction. Table deletion also owns its transaction. Preserve historical order snapshots. See `docs/menu-management.md` for contracts and learning exercises.

## Tables and Public Menu Rules

Table labels are trimmed, 1–50 characters, and unique per restaurant with case-sensitive comparison. Rename and enabled-state writes update only their own field under the table row lock. QR tokens are server-generated random 32-byte Base64URL values and remain fixed until physical deletion; no rotation endpoint exists. Reuse the deletion service without an outer transaction; active sessions prevent deletion, while closed sessions retain snapshots with a null table link. Public bootstrap resolves ownership only from the QR token and reads entrance plus menu in one Repeatable Read transaction; `MenuReader` does not start its own transaction. It exposes no join codes, orders or account information and creates no sessions. Suspended restaurants and disabled tables still expose their menu with an explanatory status. Guest UI always offers zh/it/en, remembers explicit choices per restaurant, and otherwise uses the owner's preference. A confirmed invalid QR replaces cached menu data; network failures keep earlier data with a warning. QR PNGs are generated locally with `qrcode`; optional `VITE_PUBLIC_BASE_URL` must be an HTTP(S) origin. See `docs/tables-public-menu.md` for contracts, LAN setup and learning exercises.

## Dining and Guest Access Rules

Opening acquires restaurant SHARE then table UPDATE locks; guest joining/code reading acquires restaurant, table and session SHARE locks in that order. Join codes are optional per restaurant: `Restaurant.JoinCodeRequired` (default true) is changed only by the platform, at creation or through `PATCH /api/platform/restaurants/{id}/join-code-required`. Opening always generates and encrypts a code, so switching codes back on works for active sessions, but returns `joinCode: null` and the floor hides codes while they are off. Join reads the switch under the restaurant SHARE lock and then ignores any submitted code; entrance, session and rate-limit checks still apply. Turning codes back on keeps already issued guest grants. Without codes the guest page joins automatically at most once per visit and page, then falls back to a join button, so tabs at different tables never take the guest cookie back and forth. The public bootstrap and floor expose only `joinCodeRequired`, never a code.

EMPTY closure shares `BillingService`'s closure path with PAID/VOIDED: it owns a transaction and takes the same session UPDATE lock ordering, kitchen transitions and checkout use. It requires confirmed version, zero amount, guests-left confirmation and no orders of any status; it clears the code ciphertext without incrementing BillVersion. Never reopen a closed session. Join codes use purpose-bound Data Protection, not plaintext or password hashes.

The Browser authentication selector routes `/api/public/*` to Guest and other requests to Store. Guest cookies are HttpOnly, scoped to `/api/public`, with fixed 12-hour tickets; each protected operation validates the bound session against current database state. Guest and store CSRF tokens are fetched from their respective endpoints and must use the matching identity. `publicRequest` remains anonymous; `guestRequest/guestWrite` carry credentials without store-auth failure handling. Guest query keys use `guest` plus restaurant/table/session IDs, survive store identity changes and are cleared on guest invalidation; never persist code values or tickets. Automatic recovery of unknown writes uses GET only. Ordering alone permits an explicit manual retry with the original persisted request ID and body; never automatically resend POST. Guest code displays discard late responses on lifecycle/visibility changes. See `docs/dining-guest-access.md` for contracts, state gates, testing and development activation.

## Cart and Ordering Rules

Order creation derives the restaurant/table/session from `GuestIdentity` and locks restaurant SHARE → table SHARE → session UPDATE. Validate ACTIVE and binding, then return an existing `(session_id, client_request_id)` order before applying first-submission input, service, availability or price gates. Menu writers take restaurant UPDATE; keep this coordination so snapshots and price checks cannot race. Save the whole order and increment BillVersion once in one transaction. Read orders while holding session SHARE; active authorized guests can read during service/table/ordering pauses. Never expose client request IDs in order DTOs. Pagination uses `(created_at, id)` descending, default 50/max 100; totals sum uncancelled order items, preserving original order totals. Ordering continues to use its existing tables; the separate restaurant subscription feature adds one table.

Carts are isolated by tab and restaurant/table, retaining the observed session (null before opening). Explicitly confirm the first opened visit; never migrate an old visit's draft. Limit 30 lines, 1–20 per line, 100 portions, 200-character remarks and 500-character order notes; protect line/order/accumulated bill totals against JavaScript safe-integer overflow. Use secure `getRandomValues` UUIDv4 for HTTP LAN support. Persist and read back the full intent before POST; blocked storage permits editing but prevents submission. Pending intents freeze edits. Automatic recovery revalidates access then queries the original ID; 404 is only “not found yet”. Manual retries use identical ID/content and fresh CSRF. A rejection after an unknown result does not release the intent. Reauthentication keeps local intent but hides/removes protected responses; confirmed closure clears the visit and directs unknown results to staff. Cancel requests and discard late responses on identity/lifecycle changes. See `docs/cart-ordering.md` for the four implementation steps, experiments and validation.

## Kitchen and Cancellation Rules

Kitchen queries derive restaurant identity from `CurrentAccount`. Lists contain only ACTIVE sessions and two order summaries: NEW (at least one NEW item), PROCESSED (all items terminal). NEW sorts by creation time/ID ascending; PROCESSED by processed time/ID descending. Read rows/counters in one Repeatable Read snapshot; cursors bind restaurant/status. `createdOrderCount` counts all existing orders, including processed and closed visits; item processing never changes it.

Each OrderItem has NEW/READY/CANCELLED, ReadyAt and CancelledAt. Process the whole line quantity, with no partial portions. STAFF/OWNER can only change NEW to READY or CANCELLED; neither can cancel READY. Cancellation needs human confirmation but no reason. Resolve restaurant/order/item binding before taking only session UPDATE; never lock restaurant/table afterwards. Conditional item UPDATE, summary NEW/PROCESSED and ProcessedAt, and cancellation BillVersion +1 commit together. READY does not increment BillVersion. Duplicates/races return ORDER_ITEM_CHANGED; missing/foreign/misbound items return ORDER_ITEM_NOT_FOUND. Closed sessions reject writes; paused entrances do not block existing work. Keep original snapshots and TotalAmountCents; payableAmountCents sums uncancelled items. Legacy order CancelReason is read-only, and migrated cancelled items may retain ReadyAt.

Kitchen cards retain terminal lines compactly in their original order while anything is NEW; processed cards show full details. Cancel is a secondary menu with ConfirmDialog. No whole-order write endpoints, separate cancelled tab, undo or paid-item waiver exist. Persist only order/session/item IDs and action kind before writes; one pending operation blocks its order. Recover through GET of the original order/item, never POST. Legacy markers use null itemId for GET-only review. Cancel late responses on lifecycle/identity change and invalidate kitchen, floor, dining and billing queries after writes.

Kitchen polls every 10 seconds only while visible/online and refreshes all loaded pages. A stale (30-second) or failed view blocks writes, and so does one not yet re-polled since load or foreground resume; report that only once it outlasts a short grace (`syncIsStalled`), or at once when offline/failed, so routine refreshes never flash warnings. Sound is on by default; browsers allow audio only after a user gesture, so any tap on the page starts it and a notice asks for one while it cannot play. Status tabs share one arrival baseline because the created count is restaurant-wide; first load, foreground resume and reconnect establish a silent baseline. Persist only minimal pending action identifiers per tab/restaurant/account, before the POST, but show a marker only once its result is unknown; recovery is GET-only and fresh writes require human confirmation. Cancel late work on lifecycle/identity changes. See `docs/kitchen-cancellation.md` for contracts and learning experiments.

## Billing and History Rules

Active bills are STAFF/OWNER readable; PAID closure and full closed history require OWNER. Bill reads hold session SHARE; PAID/VOIDED closure holds only session UPDATE and never takes restaurant/table row locks afterwards. Recompute uncancelled-item amount, item counts and version inside the transaction. Summaries retain orderCount and expose itemCount/newItemCount/cancelledItemCount (lines, not portions). PAID requires positive receivables and no NEW items; VOIDED requires existing orders with every item CANCELLED, zero total and guests-left confirmation. EMPTY remains limited to no orders of any status. Paused entrances do not prevent closure. Persist CLOSED, reason, total, closing time and null code ciphertext atomically without incrementing BillVersion. Identical closure type/version/amount on an already closed session returns its stored result; mismatches cannot rewrite it. Clamp closing time to the latest business timestamp.

Bill orders page ascending by creation time/ID, default 50/max 100; cursors bind tenant, session, active/history mode and bill version. BILL_CHANGED returns currentBill and resets loaded bill pages. History uses stored snapshots/closed totals, exact trimmed case-sensitive historical table labels and closure reasons. Default dates are the restaurant's local today; explicit dates are a paired inclusive range converted to UTC boundaries with DST. History sorts closed time/ID descending; cursors bind tenant and resolved filters, retaining date bounds across midnight.

Keep selected session IDs in URL search. Freeze confirmation version/amount; polling must not silently replace them. Active bill polling is 30 seconds while visible/online; stale, failed and resumed-but-not-refreshed views cannot close, reported through `syncIsStalled` like the kitchen. Persist only session ID/closure kind per tab/account/restaurant; unknown closures recover by GET of the original session, never automatic POST. Clear protected guest state through existing lifecycle checks and invalidate affected private queries after closure. See `docs/billing-history.md` for contracts, experiments and validation.

## Platform Administration

`Platform/` owns the independent Platform cookie, bootstrap/recovery CLI and restaurant/account management. Browser selects Platform for `/api/platform`, Guest for `/api/public`, Store otherwise. Platform has a persistent cookie with a fixed 30-day ticket, no sliding renewal and its own limiter; every request verifies active state and credential version. CSRF additional data binds all tokens, including anonymous tokens, to the three scopes. Platform does not grant store business permissions. Use `CurrentPlatformAccount` only for platform administration and `CurrentAccount` for OWNER staff maintenance.

Create the client-selected restaurant UUID and both store accounts atomically: SUSPENDED, ordering off, EUR/Europe/Rome, first password change required. Generated temporary passwords appear only in the successful create/reset response. Expected target credential versions protect reset/active writes; use ACCOUNT_CHANGED for target conflicts, never the current-user credential error. Suspend locks the restaurant and closes ordering; enabling ordering checks ACTIVE under that same lock. Restoring ACTIVE does not enable ordering.

Restaurants carry an optional `GoogleMapsUrl`, reserved for a future public restaurant list. It is set at creation or through `PATCH /api/platform/restaurants/{id}/google-maps-url` (blank clears it), which updates only that column. `InputRules.IsGoogleMapsUrl` accepts only HTTPS Google Maps links (`maps.app.goo.gl`, `maps.google.*`, `google.*/maps`) up to 2048 characters, because pages render it as a plain href. Only the platform `RestaurantSummary` returns it and only platform pages show it; store, guest and subscription responses never include it.

The join-code switch follows the map-link pattern: a single-column update that waits for guest joins' restaurant SHARE locks, logs the actor and sends the target value, behind the inline `管理操作确认`.

Frontend `features/platform/` uses separate identity, request/CSRF functions and `platform` query keys; `/staff/settings` is OWNER-only. Use direct promises for secret-bearing writes; never cache or persist temporary passwords. Cancel late work and clear secret displays on navigation, identity and visibility changes. Persist only scoped pending identifiers/expected versions before writes. Recover through GET; create retries need explicit confirmation and the original UUID. Reset recovery compares versions but cannot recover a lost password or prove which administrator changed it. Other identities' caches and pending markers must survive unrelated login/logout. See `docs/platform-pilot.md` for contracts and exercises.

## Restaurant Subscription Rules

Platform manages free-text owner contact and the default annual fee. OWNER reads only its restaurant through `GET /api/owner/subscription` and has no subscription writes; STAFF and Guest never receive subscription/contact information. `features/subscriptions/` owns platform period forms, the OWNER `/staff/subscription` page and visible/online 60-second reminders. Private queries include restaurant/account IDs; platform queries retain the `platform` prefix.

Each non-overlapping service period stores inclusive start, exclusive end, agreed years and whole-period EUR integer cents. Nullable `PaidOn` is the only payment-state source; one full collection per period. Collecting money never shifts agreed dates. Renewal adds a period; changing default annual fee never rewrites existing agreements. Paid amount/date are frozen; the dedicated expiry endpoint is the only change a paid period accepts. Service expiry and unpaid periods only warn and never automatically change restaurant service or ordering. Contiguous periods extend the displayed final expiry; gaps retain expired warnings until service resumes. Due reminders begin seven days before the exclusive cutoff; started unpaid periods remain due even after expiry. V1 keeps no change history or owner inbox.

Reads return the summary and every period from one Repeatable Read snapshot, without paging. All subscription writes own a transaction, lock restaurant UPDATE, require the expected subscription version, increment it only when something changed and return the fresh detail. The version is the only duplicate guard: a lost, repeated or late request applies only to the state it was confirmed against, so at most one write per version succeeds and the rest receive `SUBSCRIPTION_CHANGED`, a target conflict, never an identity failure. Subscription writes are therefore the exception to persisted unknown-result markers: the browser stores nothing, refreshes after an unknown result and requires a fresh human confirmation. Build initial periods/payments in the same transaction as restaurant and accounts. Each applied write logs the platform actor, restaurant and action, never amounts or contact. See `docs/restaurant-subscriptions.md` for contracts and validation.
