# Repository Guidelines

## Project Structure & Module Organization

- `TavoloFlow.slnx` groups the backend projects; `global.json` specifies the .NET SDK.
- `backend/TavoloFlow.Api/` contains the ASP.NET Core 10 controller-based API. Startup lives in `Program.cs`; `Entities/` contains eighteen persistence entities, and `Data/` contains `ApplicationDbContext`, EF Core mappings and migrations, the row-lock helpers (`RowLocks`) and catalog deletion services. `Common/` holds cross-cutting code: the `ApiError` envelope with `ApiException` and its global filter, browser identity selection and CSRF scoping (`BrowserSecurity`), keyset paging, enum text (`ApiEnum`: uppercase names with an underscore between words, such as `DINE_IN`), input rules and the fixed-window rate limiter. `Accounts/` implements development account initialization, store authentication and authorization; `Controllers/AuthController.cs` exposes the account endpoints. `Menus/` implements menu maintenance, availability, dish photos (`MenuImages`), the shared option groups (`MenuOptionService`; every menu write locks through `MenuWrites`), language rules and anonymous menu reading; `Tables/` implements table maintenance. `Dining/` implements opening tables, the shared session bill summary (`BillSummaryResponse`), encrypted join codes and the entrance rule; `Guests/` implements guest authentication, access checks and join rate limits. The corresponding controllers expose store and public APIs separately. `Ordering/` implements idempotent guest ordering, option pricing (`OrderOptions`), the order lines shared with online requests (`OrderLines`: format, menu and price check, `OrderLineSnapshot` snapshots), immutable snapshots and cursor-paged table orders; `Dining/` also owns the accepting-orders switch. `Kitchen/` implements the staff queue, conditional item READY/cancellation transitions, transactionally updated bill versions and the pass queue with its served writes. `Billing/` implements active bills, all four closures (PAID/VOIDED/EMPTY/NO_SHOW) and owner-only closed history; the system records confirmation of offline payment, not payment transactions. `Platform/SubscriptionService` owns restaurant service periods and offline annual fee collection. `Online/` owns online ordering: the weekly hours calendar (`OnlineSchedule`), the single availability rule (`OnlineAvailability`), the single waiting/expired rule for online requests (`OnlineRequestState`), the OWNER/STAFF settings (`OnlineSettingsService`), the anonymous online menu, submission with recovery and status page (`OnlineMenuService`, `OnlineRequestService`, `OnlineOrderStatusService`, `Controllers/OnlineOrderController.cs`), and the staff decisions: pending and in-progress lists, acceptance and rejection (`OnlineStaffService`, `Controllers/OnlineOrdersController.cs`). `Push/` owns lock-screen push for new online orders: the VAPID key (`PushKeys`), the accepted push services (`PushEndpoints`), device registration (`PushSubscriptionService`, `Controllers/PushController.cs`), the single rule for devices that no longer receive (`PushTargets`) and best-effort sending (`PushQueue`, `PushSender`).
- `backend/TavoloFlow.Api.Tests/` contains data-layer, account, menu, table, public-menu, dining, guest, ordering, kitchen and billing integration tests using disposable PostgreSQL containers and `WebApplicationFactory`.
- `frontend/src/` contains the React/TypeScript application. `routes/` defines TanStack file-based routes; `router.tsx` creates the router from the generated `routeTree.gen.ts`. Account pages, identity queries and the installable staff app hook live in `features/accounts/`; menu maintenance and the option library (with its group templates) live in `features/menu/`, table maintenance and QR generation in `features/tables/`, and anonymous guest browsing in `features/public-menu/`. `features/dining/` provides `/staff/floor` (state and writes in `useFloor.ts`); `features/guests/` manages guest verification and visit lifecycle on the public menu; `features/orders/` provides the option picker and its pure rules (`options.ts`), tab-local carts, order confirmation, table orders and durable unknown-result recovery within `/q/{token}`. `features/kitchen/` provides `/staff/kitchen`, paged queue polling (`useKitchen.ts`), per-screen categories (`useKitchenCategories.ts`), arrival chimes (`useKitchenChime.ts`), cancellation confirmation, GET-only recovery and device-controlled audio; `features/pass/` provides the `/staff/pass` counter-tablet screen of dishes waiting to be served. `features/online/` provides `/staff/online` (waiting requests with accept and reject, accepted orders in progress, `useOnlineOrders.ts`), the pending banner with its ringing on every staff page (`OnlinePendingBanner.tsx`), `/staff/online-settings` (link, QR, pause, OWNER phone and hours) and their pure rules (`state.ts`); `lib/session-label.ts` and `components/session-name.tsx` name a session in every channel (a table, or an online number with customer name and estimated time) for the kitchen, pass, bills and history; `features/push/` provides the lock-screen notification switch on 首页 (`PushSection.tsx`, `usePushSubscription.ts`), the shared controller and foreground reconciliation (`controller.ts`, `PushProvider.tsx`, `usePushSync.ts`), the browser helpers (`device.ts`) and pure rules (`state.ts`); `features/online-order/` provides the anonymous customer pages `/r/{slug}` (menu, cart and checkout, `useOnlineCart.ts`), `/r/{slug}/privacy` and `/o/{token}` (order status), with their pure rules in `state.ts`. Both pages share `lib/alert-sound.ts`/`lib/useAlertSound.ts` for their chimes. `features/billing/` provides `/staff/orders`, `/staff/history`, shared floor bill/zero-closure panels and GET-only closure recovery. Shared HTTP/CSRF/error handling lives in `lib/api.ts`; every hook that writes tracks its in-flight requests with `lib/useOperations.ts` (pure tracker in `lib/operations.ts`), kitchen and billing persist unknown-result markers with `lib/usePendingMarkers.ts`, and `lib/store-views.ts` builds the store query keys that service writes refresh across pages; shared shadcn UI lives in `components/ui/`, app-wide composites (page header, notices, confirmation dialog, list/detail layout, filter chips, loading/empty states, brand mark, source link) in `components/`, utilities in `lib/`, and the theme tokens in `index.css`. `features/accounts/navigation.ts` lists the store navigation, from the role and service rules in `features/accounts/state.ts`. `lib/theme.ts` lists the restaurant colour presets and `lib/useDocumentTheme.ts` applies one. `frontend/public/` holds the favicon, the staff PWA manifest, the service worker and the app icons.
- `docs/README.md` indexes two layers. `docs/reference/` holds the English-only reference: product requirements, the feature contracts and the DBML schema/ER diagram; keep it in one language and update it with behavior changes. `docs/it/` holds the user's own guides (`development-notes.md`, `self-hosting.md`, `local-development.md` with demo, development setup, tests and phone testing, and `learning-notes.md`), which are the definitive overview, deployment and local-run docs. Italian is the source; `docs/zh-CN/` and `docs/en/` translations use the same filenames. Root `compose.yaml` defines local PostgreSQL. `deploy/` contains the separate production Compose, Docker builds, Caddy configuration and explicit release/backup/recovery commands; `deploy/smoke-test.sh` verifies a release package end to end in disposable containers.
- `.github/workflows/ci.yml` runs the backend and frontend checks listed below on every push to `main` and pull request; `demo-images.yml` publishes the three demo images (`tavoloflow-demo-init`, `-api`, `-web`) to GHCR for each `v*` tag, built natively for amd64 and arm64, which `demo/compose.yaml` pulls before falling back to a local build. `docs/images/` holds the README screenshots, the walkthrough animations and the GitHub social preview, composed from the Demo Ramen screenshots of the marketing-site repository; regenerate them after visible UI changes. `CONTRIBUTING.md`, `SECURITY.md` (private vulnerability reporting and scope) and `.github/ISSUE_TEMPLATE/` are for outside contributors.
- A deployment serves business routes and `/api` from one public HTTPS origin: `PUBLIC_ORIGIN` at build time (required, no default) and the matching `DOMAIN` on the server. The maintainer's hosted service runs at `https://app.qiaotavoloflow.it` on a netcup VPS, always on this repository's code, with a separate marketing site on the apex domain. Other sites on the parent domain stay separate: this repository must not serve their hosts or add parent-domain cookies/CORS to connect them.

## Build, Test, and Development Commands

Run backend and infrastructure commands from the repository root:

- `cp .env.example .env`: initialize local database settings; replace the password before starting PostgreSQL.
- `docker compose up -d db`: start PostgreSQL on localhost port 5432.
- `dotnet build TavoloFlow.slnx`: restore dependencies and build the backend solution.
- `dotnet run --project backend/TavoloFlow.Api --launch-profile https`: start the API at `https://localhost:7298`.
- `dotnet run --project backend/TavoloFlow.Api --launch-profile http`: start the API at `http://localhost:5093` for the Vite `/api` proxy.
- `dotnet run --project backend/TavoloFlow.Api --launch-profile http -- --seed-dev-accounts`: explicitly initialize Development accounts after configuring `DevelopmentSeed` and applying migrations; see `docs/reference/accounts-platform.md`.
- `dotnet test TavoloFlow.slnx`: run backend tests.
- `dotnet csharpier format .` (or `dotnet csharpier check .`): format (or check) the C# code with CSharpier.
- `docker compose -f demo/compose.yaml up -d --build`: build and start the isolated local Demo Ramen experience, without a host SDK or `.env`. Its one-shot `init` explicitly runs the migration bundle and `--seed-demo`; the API never migrates on startup. `down` retains demo data and `down -v` explicitly resets only that Compose project's volumes. See `docs/it/local-development.md`.

From `frontend/`, run `npm install` to install dependencies, `npm run dev` for development, `npm run build` for TypeScript checking and production output, `npm run lint` for Oxlint, `npm run format` (or `npm run format:check`) for Prettier, and `npm run preview` to preview the build.

The build runs `vite build && tsc -b`: Vite generates the route tree before TypeScript checks route types. Commit `src/routeTree.gen.ts` with route changes; never edit it manually. It is excluded from lint. The TanStack Router Vite plugin must precede the React plugin and enables automatic route code splitting.

## Coding Style & Naming Conventions

Use four-space indentation in C# and two spaces in TypeScript/TSX. Use PascalCase for C# types/methods and React components; use camelCase for JavaScript functions and variables. Prefer file-scoped C# namespaces and preserve nullable annotations. Use `@/` imports for frontend source paths. Frontend files are formatted with Prettier (`frontend/.prettierrc.json`, print width 100); run `npm run format` before committing. C# is formatted with CSharpier, pinned as a local .NET tool (`.csharpierrc.json`, print width 100, matching Prettier); `.csharpierignore` excludes the EF Core migrations. Run `dotnet csharpier format .` from the repository root before committing; `.vscode/settings.json` also formats C# on save through the CSharpier extension. Oxlint checks React hooks and TypeScript rules.

Keep route files thin: URL/search configuration belongs in `routes/`, while forms and feature state belong in the corresponding `features/` directory. `AuthBoundary` observes the shared identity query; do not duplicate authentication requests in route loaders. Public menu routes do not use `AuthBoundary` or request `/me`. The store layout sets available width, and pages choose their own card width. Menu/table editing keeps its local form snapshot during background refresh; private query keys include restaurant and account IDs. Public queries use the `public` prefix and survive account changes; `publicRequest` omits credentials and store-auth failure handling. Writes have no automatic retry or offline queue. Add UI components with the existing shadcn CLI configuration (Base UI, `base-nova`) and answer “no” when it offers to overwrite `button.tsx`: style utilities stay separate from component exports for Fast Refresh (`button-variants.ts`, `toggle-variants.ts`). Links styled as buttons use TanStack `Link` with `buttonVariants`, which merges conflicting classes exactly as `Button` does. Preserve labels and focus styles, and follow the UI conventions below. The `Route` export lint exception applies only to route files.

## UI Conventions

The visual system is a warm trattoria: cream surfaces and terracotta actions, defined as semantic tokens in `index.css`; components use tokens and variants, never raw colours. Each colour has one meaning everywhere: `warning` (saffron) is waiting, new or due soon; `success` (basil) is ready, available or paid; `destructive` (tomato) is cancel, void or delete; muted is cancelled or disabled. Guests see NEW as a neutral “received”, not a warning. Restaurant themes (`[data-theme]` blocks in `index.css`, chosen per restaurant by the platform) replace only the brand palette (surfaces, text, primary, accent, borders) and never the state colours, radius, fonts or layout; `tests/theme.test.ts` enforces WCAG AA text contrast and keeps every primary apart from the state colours. The theme is set on `<html>` (`useDocumentTheme`) so portals follow it, only by signed-in staff pages, a loaded guest menu and the loaded online customer pages; sign-in, first password change and platform pages keep the default. V1 has no dark theme; keep the class-based `dark` variant so component `dark:` styles never follow the OS. Text is Geist with the platform CJK font; `font-display` (Fraunces) is only for the brand wordmark, the guest menu's restaurant and category names and printed table cards.

Interface language: every store page (OWNER and STAFF) and every platform page is in Chinese, Italian or English (`Language` in `lib/language.ts`, the same type the guest menu uses). The choice is one device preference shared by store and platform pages, like the kitchen sound, with no database or API field: `lib/staff-language.ts` stores it in `localStorage` (`tavoloflow:staff-language`) and survives logout, so a shared tablet keeps it for everyone. Without a valid stored choice, or when storage is unreadable, pages follow the first supported language in `navigator.languages` (`browserLanguage`), and English otherwise. `useStaffLanguage()` reads it and `LanguageSwitch` changes it, shown under the brand before store sign-in (login and first password change), in 首页's account card and in the platform header; `StaffLayout` and `PlatformLayout` set `<html lang>` (`htmlLang`). Each feature keeps all three languages in its `messages.ts`; copy shared by several store pages lives in `lib/staff-messages.ts`. Add every new string in all three languages. The server writes errors in English for developers, so `errorMessage(error, unknownResult, language)` never shows the server text: it translates the code through the `errorTranslations` tables (`lib/api-messages.ts`) in every language, with a generic fallback, and `fieldErrors` only marks the fields. The Italian and English tables are typed by the Chinese one, so a missing translation fails `tsc`; add every new store or platform error code to all three. Shared components (`ConfirmDialog`, `MasterDetail`, `DialogContent`, `SheetContent`, `SubscriptionStatus`, `PeriodDetails`, `TemporaryPasswords`, `AccountActions`) read `useStaffLanguage()` for their own default labels, so store and platform pages pass labels only when the text differs; guest pages, which have their own language, always pass theirs. Dish names and allergens on store pages follow the interface language through the usual name fallback, and money/time formats follow it too (dates use `zh-CN`, `it-IT` and `en-GB`). Copy is adapted to the space, never literal: tab labels stay one short word (Home · Sala · Cucina · Conto · Menu; Home · Floor · Kitchen · Bill · Menu), and badges, tabs and toggles (`whitespace-nowrap`) take one or two words. Check new copy at 360px in every language.

Base controls are touch-sized: buttons, inputs, selects, tabs and toggles reach 44px and checkboxes/switches have 44px hit areas, so call sites never add heights. Design mobile first. Phones show the store tabs as a bottom bar and tablets/desktops (≥md) as a side rail; both render `staffNavItems(account)`, whose fourth tab is the role's own service job (Bill for OWNER, Pass for STAFF) while the others keep their places, and less frequent pages are reached from 首页 (`staffManagementItems`). The pure `features/accounts/state.ts` decides both lists from the role and the restaurant's services: Floor and Tables exist only with QR dine-in (online-only restaurants get four tabs), online ordering adds the Online orders (`/staff/online`) and Online ordering settings (`/staff/online-settings`) entries to 首页 for both roles and the pending banner to every staff page, and a page whose service is off renders `ServiceNotOffered` for saved links. Pages outside the tabs show a `PageHeader` back link, because an installed web app has no browser back button on iOS. Use `min-h-dvh`; fixed bars use `pt-safe`/`pb-safe` or `env(safe-area-inset-*)`.

Compose pages from `src/components/`: `PageHeader`; `Notice` for all inline feedback (errors are `role=alert`, other tones `role=status`); `ConfirmDialog` for the human confirmation in front of irreversible or money-related store writes (open a table, close a bill, cancel an order, delete, reset a password); `MasterDetail` for a list and its selected record, a non-modal column at ≥lg (`WIDE_SCREEN` in `lib/useMediaQuery.ts`) and a full-height sheet below, selected through the route's `sessionId` search where it has one; and `FilterChips`, `LoadingState`, `EmptyState`, `BrandMark`. `SourceLink` is the AGPL-3.0 section 13 source offer (`SOURCE_CODE_URL` in `lib/brand.ts`): the guest menu footer, every online customer page, staff sign-in, 首页 and every platform page show it, so keep it when restructuring them. Wide screens never use a modal for a detail view: Base UI modals mark the rest of the page `aria-hidden`. The guest page renders `CartPanel` once: a sticky column at ≥lg, otherwise a bottom sheet opened from `CartBar`.

Platform confirmations stay inline regions (the management and subscription confirmations, labelled in the interface language); creating a restaurant together with its first period still uses `window.confirm` (platform administrators only). The staff area is an installable PWA (`docs/reference/pwa.md`); the platform stays a website. Lock-screen push exists only for new online orders (Online Ordering Rules); kitchen, pass and every other feature never push. Only `StaffLayout` links `/staff.webmanifest` and, in production builds, registers `/sw.js` with scope `/staff` (`features/accounts/useInstallApp.ts`). Never link a manifest from `index.html`, guest, online customer or platform pages, so guests on `/q/*` and customers on `/r/*` and `/o/*` are never offered an installation. The manifest id, start_url and scope stay `/staff` without a trailing slash, because the router drops trailing slashes and `/staff` must stay inside the app. The worker handles navigations only, network first with a built-in offline page, and uses no Cache Storage: never cache `/api`, pages or assets. Its standalone offline HTML follows the same saved-language → browser-language → English preference rule without loading app assets. It also shows push notifications (text in zh/it/en inside `sw.js`, chosen by the payload's language, tag `online-order-{number}`; a malformed payload still shows a notification, because browsers require one per push) and opens `/staff/online` on a tap, focusing an open staff window first. Its top level only declares constants and calls `addEventListener`, so `tests/pwa.test.ts` can run it in a sandbox. The home page offers Chromium's install prompt, or per-device steps elsewhere. iOS uses the opaque `apple-touch-icon.png`. The kitchen's hidden categories and the kitchen's and pass screen's sound and keep-screen-on switches (`lib/useAlertSound.ts`, `lib/useWakeLock.ts`) store only device preferences in `localStorage`. The online order ringing has no switch (`useAlertSound(null, …)`), and those switches never mute it.

## Testing Guidelines

Backend tests use xUnit, Coverlet, and Testcontainers.PostgreSql. The existing integration tests require Docker and apply real migrations to a disposable PostgreSQL database, separate from the development database. Write meaningful assertions; name new classes `<Subject>Tests` and methods `Method_Scenario_ExpectedResult`. Collect coverage with `dotnet test TavoloFlow.slnx --collect:"XPlat Code Coverage"`; no minimum threshold is configured. No frontend test framework is installed. With Node 24, run `node --test --test-isolation=none tests/*.test.ts` from `frontend/` for pure language, QR URL, query-scope, dining recovery, cart/order recovery, online cart/checkout/status-page, kitchen synchronization and billing confirmation/recovery logic, the staff language preference, plus the PWA manifest/icon invariants, the service worker's push and notification-tap handlers, the push switch rules, the shared push controller (registration, retry, logout) and the browser subscription read, and the theme palette contrast checks; also run build/lint and manually verify affected UI flows.

## Commit & Pull Request Guidelines

History uses short, scoped messages such as `backend: docker postgresql setup` and `docs: er-diagram`; follow that pattern. PRs should describe behavior changes, link relevant issues, and record validation commands/results. Include screenshots for visible UI changes and configuration or schema notes where relevant.

## Security & Configuration

Keep credentials in ignored `.env` files, environment variables, or .NET user secrets. Commit only safe example values. Docker Compose settings do not automatically configure the API connection string. Store authentication uses an HttpOnly persistent cookie with a fixed 30-day ticket, no sliding renewal and CSRF validation on controller writes. Store and Platform passwords accept 6–128 characters, including six digits, and cannot be entirely whitespace. Use `CurrentAccount` for trusted restaurant identity and the store authorization policies for business endpoints; only self-account operations may bypass the first-password-change requirement. Data Protection keys must stay outside Git and persist across restarts; so must the VAPID push key (`VAPID_PRIVATE_KEY` in the production `.env`, 64 hex characters from `openssl rand -hex 32`, checked for format and the P-256 scalar range by the installer before stopping the old API, and required by the production Compose, which passes `https://{DOMAIN}` as the push subject), because a new key makes every staff device turn notifications on again. Never add automatic startup migrations or log passwords, tickets, join codes or request bodies. Production templates live in `deploy/`; never merge them with the local database Compose. Production uses a trusted Caddy proxy, persistent Data Protection keys and explicit migration bundles. Never expose database/API container ports or apply migrations automatically at startup.

## Local Demo Rules

`demo/` is a separate local-only Compose project with editable JSON fixtures, bundled AI-generated WebP dish photos and image prompts. `--seed-demo` runs only in Development and uses the existing CLI maintenance path; the API has no demo mode or special authentication behavior. The seeder skips before reading fixtures if any restaurant or platform account already exists, and imports into an empty business database in one transaction. Decode photos before the transaction through the ordinary `MenuImages` pipeline. Normal use has one init task; concurrent initialization is not supported. No metadata table or production migration is added. Keep demo assets and public credentials out of normal production image payloads. No visits, orders or bill history are preloaded. Use `http://127.0.0.1:8080` for the demo and `localhost` for ordinary development, or separate browser profiles, to avoid cookie collisions.

## Menu Rules

Category display order is one restaurant-wide `menu_categories.position`, shared by staff, QR and online menus in every language. `MenuReader` sorts categories by position then ID and dishes by that category order, then their category-local position and ID. New categories append under the restaurant UPDATE lock, name edits preserve position and deletion may leave gaps. OWNER reorders with `PUT /api/owner/menu/categories/order` and the complete `categoryIds` list; missing, duplicate, extra or foreign IDs reject atomically with `CATEGORIES_CHANGED`. The migration preserves each restaurant's previous ID order. Positions are non-negative without a unique constraint; same-set concurrent reorderings use last-write-wins. The menu's inline category list saves each up/down move immediately and leaves the "All dishes" filter first. Demo imports assign positions from fixture order.

Dish order is category-local `menu_items.position`. Creating a dish or changing its category appends under the restaurant UPDATE lock; same-category edits preserve position, and deleting/moving leaves gaps. OWNER submits the complete `itemIds` list to `PUT /api/owner/menu/categories/{categoryId}/items/order`; include sold-out and unreviewed dishes. Missing/foreign categories return `MENU_RESOURCE_NOT_FOUND`; invalid or stale membership returns `CATEGORY_ITEMS_CHANGED` atomically. Set consecutive positions from zero and batch only changed rows through one `SaveChangesAsync`. Sorting changes no other fields or option links and needs no allergen review. The migration preserves ID order per restaurant/category; demo dishes use fixture order. The OWNER's existing editor sheet keeps an in-memory draft, uses up/down controls and saves once. Background reads preserve that draft; failures freeze it until an explicit GET reloads and resets it. No automatic write retry or persisted draft exists; `useItemOrder` tracks work through `useOperations` and ignores late identity/unmount results.

Menu content and availability writes derive the restaurant from `CurrentAccount` and lock its restaurant row before category/item rows. Default language is a stable OWNER preference (`zh`/`it`/`en`), updated only through its setting endpoint, even on empty menus; content changes never repair or replace it. Reads use a repeatable-read snapshot and derive read-only `availableLanguages` from loaded names. General name fallback is default → Italian → Chinese → English, deduplicated; the staff UI puts its own interface language before this chain. Descriptions follow the resolved name language. Item content DTOs exclude availability; the dedicated availability endpoint updates only that field. Every item content save requires allergen review, even when sold out. Keep price inputs in decimal strings and send integer cents within JavaScript’s safe range. `CatalogDeletionService.DeleteMenuItemAsync` always owns its transaction and locks the restaurant before the item; do not wrap it in an outer transaction. Table deletion also owns its transaction. Preserve historical order snapshots. Dish photos are optional, one per item, OWNER-only and written through their own `PUT`/`DELETE .../items/{id}/image` endpoints, never the content DTO, so a photo change needs no allergen review; they take the same restaurant-then-item lock order, but `MenuImages` decodes outside the transaction. The server accepts JPEG/PNG/WebP up to 15 MB, applies EXIF orientation, crops a centred 640×640 WebP without metadata and never serves uploaded bytes. Bytes live in `menu_item_images`, so menu reads never load them; `menu_items.image_id` changes only together with that table. Each upload gets a new random id, so `GET /api/public/menu-images/{id}` is `immutable` (Caddy's dedicated route keeps `/api`'s no-store off it) and replaced URLs return 404. Item deletion cascades the photo; order snapshots never include it, and the browser persists no marker for photo writes. `deploy/Dockerfile.api` publishes the API for `linux-x64` only, because SkiaSharp otherwise ships every platform's native library. See `docs/reference/menu-tables.md` for contracts and verification entry points.

## Menu Options Rules

Options are generic, never drink-specific: the same mechanism serves bubble tea sizes, sweetness, ice and toppings and ramen spice levels and extras. `menu_option_groups` is a restaurant-wide library that dishes share through the pure join table `menu_item_option_groups`; each group's `min_select`/`max_select` is its whole rule, and its options (`menu_options`) carry a non-negative `price_delta_cents`, their own allergen codes and a sold-out switch STAFF may use. Display order is one restaurant-wide `position` on the group, never per dish; a dish shows its own groups in that relative order. Required groups are never preselected. Every option write locks restaurant UPDATE through `MenuWrites`, like other menu writes, so ordering's restaurant SHARE prices a consistent menu. A group save replaces the group (options sent with their id keep it and their availability; others are added or removed) and its dishes, and requires the allergen review; the reorder endpoint takes every current group id and rejects stale lists with `OPTION_GROUPS_CHANGED`. A dish's `optionGroupIds` is a required list that replaces its links (empty for none). Group, dish and restaurant deletion remove options and links through `ON DELETE CASCADE`.

Orders send a required `optionIds` list per line (empty for none); `OrderOptions.Resolve` checks every option belongs to one of the dish's groups, is available and keeps each group within its bounds, otherwise `MENU_CHANGED` with reason `OPTIONS_CHANGED`. `unit_price_cents` is the dish price plus the deltas, so bill sums never change, the allergen snapshot unions dish and option codes, and `options_snapshot` (jsonb) records group/option names and deltas in display order. Carts are version 2 with option snapshots per line and merge only identical choices; no older format is accepted, since no restaurant used the app before options. Templates (`features/menu/option-templates.ts`) only prefill a new group's form in three languages; nothing stores them. Ice and temperature share one group, so there are no rules between groups. Out of scope: option dependencies, several portions of one option, per-dish prices inside a shared group, negative deltas and combos. See `docs/reference/menu-tables.md` and `docs/reference/dining-ordering.md`.

## Tables and Public Menu Rules

Table labels are trimmed, 1–50 characters, and unique per restaurant with case-sensitive comparison. Rename and enabled-state writes update only their own field under the table row lock. QR tokens are server-generated random 32-byte Base64URL values and remain fixed until physical deletion; no rotation endpoint exists. Reuse the deletion service without an outer transaction; active sessions prevent deletion, while closed sessions retain snapshots with a null table link. Public bootstrap resolves ownership only from the QR token and reads entrance plus menu in one Repeatable Read transaction; `MenuReader` does not start its own transaction. It exposes no join codes, orders or account information and creates no sessions. Suspended restaurants and disabled tables still expose their menu with an explanatory status. Guest UI always offers zh/it/en, remembers explicit choices per restaurant, and otherwise uses the owner's preference. A confirmed invalid QR replaces cached menu data; network failures keep earlier data with a warning. QR PNGs are generated locally with `qrcode`; optional `VITE_PUBLIC_BASE_URL` must be an HTTP(S) origin. See `docs/reference/menu-tables.md` for contracts and QR behavior; local/LAN setup is in `docs/it/local-development.md`.

## Dining and Guest Access Rules

Opening acquires restaurant SHARE then table UPDATE locks; guest joining/code reading acquires restaurant, table and session SHARE locks in that order. Join codes are optional per restaurant: `Restaurant.JoinCodeRequired` (default true) is changed only by the platform, at creation or through `PATCH /api/platform/restaurants/{id}/join-code-required`. Opening always generates and encrypts a code, so switching codes back on works for active sessions, but returns `joinCode: null` and the floor hides codes while they are off. Join reads the switch under the restaurant SHARE lock and then ignores any submitted code; entrance, session and rate-limit checks still apply. Turning codes back on keeps already issued guest grants. Without codes the guest page joins automatically at most once per visit and page, then falls back to a join button, so tabs at different tables never take the guest cookie back and forth. The public bootstrap and floor expose only `joinCodeRequired`, never a code.

EMPTY closure shares `BillingService`'s closure path with PAID/VOIDED: it owns a transaction and takes the same session UPDATE lock ordering, kitchen transitions and checkout use. It requires confirmed version, zero amount, guests-left confirmation and no orders of any status; it clears the code ciphertext without incrementing BillVersion. Never reopen a closed session. Join codes use purpose-bound Data Protection, not plaintext or password hashes.

The Browser authentication selector routes `/api/platform/*` to Platform, `/api/public/*` to Guest and other requests to Store. Guest cookies are HttpOnly, scoped to `/api/public`, with fixed 12-hour tickets; each protected operation validates the bound session against current database state. Guest and store CSRF tokens are fetched from their respective endpoints and must use the matching identity. `publicRequest` remains anonymous; `guestRequest/guestWrite` carry credentials without store-auth failure handling. Guest query keys use `guest` plus restaurant/table/session IDs, survive store identity changes and are cleared on guest invalidation; never persist code values or tickets. Automatic recovery of unknown writes uses GET only. Ordering alone permits an explicit manual retry with the original persisted request ID and body; never automatically resend POST. Guest code displays discard late responses on lifecycle/visibility changes. See `docs/reference/dining-ordering.md` for contracts, state gates and verification; initialization is in `docs/reference/accounts-platform.md`.

## Cart and Ordering Rules

Order creation derives the restaurant/table/session from `GuestIdentity` and locks restaurant SHARE → table SHARE → session UPDATE. Validate ACTIVE and binding, then return an existing `(session_id, client_request_id)` order before applying first-submission input, service, availability or price gates. Menu writers take restaurant UPDATE; keep this coordination so snapshots and price checks cannot race. Save the whole order and increment BillVersion once in one transaction. Read orders while holding session SHARE; active authorized guests can read during service/table/ordering pauses. Never expose client request IDs in order DTOs. Pagination uses `(created_at, id)` descending, default 50/max 100; totals sum uncancelled order items, preserving original order totals. Ordering continues to use its existing tables; the separate restaurant subscription feature adds one table.

Carts are isolated by tab and restaurant/table, retaining the observed session (null before opening). Explicitly confirm the first opened visit; never migrate an old visit's draft. Limit 30 lines, 1–20 per line, 100 portions and 200-character line remarks (orders have no order-level note); protect line/order/accumulated bill totals against JavaScript safe-integer overflow. Use secure `getRandomValues` UUIDv4 for HTTP LAN support. Persist and read back the full intent before POST; blocked storage permits editing but prevents submission. Pending intents freeze edits. Automatic recovery revalidates access then queries the original ID; 404 is only “not found yet”. Manual retries use identical ID/content and fresh CSRF. A rejection after an unknown result does not release the intent. Reauthentication keeps local intent but hides/removes protected responses; confirmed closure clears the visit and directs unknown results to staff. Cancel requests and discard late responses on identity/lifecycle changes. See `docs/reference/dining-ordering.md` for submission, persistence and recovery contracts.

## Kitchen and Cancellation Rules

Kitchen queries derive restaurant identity from `CurrentAccount`. Lists contain only ACTIVE sessions and two order summaries: NEW (at least one NEW item), PROCESSED (all items terminal). NEW sorts by creation time/ID ascending; PROCESSED by processed time/ID descending. Read rows/counters in one Repeatable Read snapshot; cursors bind restaurant/status. `latestCreatedAt` is the newest order's creation time across both statuses and closed visits, read as one index end per status; only a new submission (or an online acceptance, which creates the order) raises it, never item processing or closure. Kitchen orders and pass items carry `channel`, a nullable `tableLabel` and, for online orders, `online { number, customerName, estimatedAt }`, never the phone or address; pages name sessions only through `lib/session-label.ts`, and cards holding `SessionName` take `min-w-0` so a long customer name cannot widen a 360px grid. The dish view keeps a short session title and adds the estimated time beside the existing wait on one line, without the customer name; the estimated time stays whole while the wait may truncate.

Each OrderItem has NEW/READY/CANCELLED, ReadyAt and CancelledAt. Process the whole line quantity, with no partial portions. STAFF/OWNER can only change NEW to READY or CANCELLED; neither can cancel READY. Cancellation needs human confirmation but no reason. Resolve restaurant/order/item binding before taking only session UPDATE; never lock restaurant/table afterwards. Conditional item UPDATE, summary NEW/PROCESSED and ProcessedAt, and cancellation BillVersion +1 commit together. READY does not increment BillVersion. Duplicates/races return ORDER_ITEM_CHANGED; missing/foreign/misbound items return ORDER_ITEM_NOT_FOUND. Closed sessions reject writes; paused entrances do not block existing work. Keep original snapshots and TotalAmountCents; payableAmountCents sums uncancelled items. Cancellation reasons are not stored or returned; migrated cancelled items may retain ReadyAt.

The default dish view groups the NEW lines of the loaded NEW orders by `menuItemId` (snapshot names once the dish is deleted), oldest wait first; it shares the NEW query and writes per item like the cards, with no batch endpoint, and pages request 100 orders so one page normally covers a small restaurant, otherwise it warns that totals may be incomplete. Per-station screens reuse menu categories, with no station entity: the dish view's category dialog checks the shown categories, but the device stores only the hidden IDs (`tavoloflow:kitchen-hidden-categories:{restaurantId}` in `localStorage`), so new categories appear everywhere. The menu is read only while some are hidden or being chosen; dishes off the menu, or before the menu loads, always show. Such a screen chimes only for its own new lines (`screenArrivals`) while every NEW order is loaded, and falls back to the restaurant-wide order watermark otherwise, so it may over-chime for that screen. Timestamp watermarks are auxiliary reminders, not durable event delivery: clock rollback or out-of-order commits can add work without advancing the maximum. The order and processed tabs stay unfiltered. Kitchen cards retain terminal lines compactly in their original order while anything is NEW; processed cards show full details. Cancel is a secondary menu with ConfirmDialog. No whole-order write endpoints, separate cancelled tab, undo or paid-item waiver exist. Persist only order/session/item IDs and action kind before writes; one pending operation blocks its order. Recover through GET of the original order/item, never POST. Legacy markers use null itemId for GET-only review. Cancel late responses on lifecycle/identity change and invalidate kitchen, floor, dining and billing queries after writes.

Kitchen polls every 10 seconds only while visible/online and refreshes all loaded pages. Polled reads stay bounded by the open visits: never count or scan a restaurant's history, read an index end instead (`latestCreatedAt`, `latestReadyAt`). A stale (30-second) or failed view blocks writes, and so does one not yet re-polled since load or foreground resume; report that only once it outlasts a short grace (`syncIsStalled`), or at once when offline/failed, so routine refreshes never flash warnings. Sound is on by default; browsers allow audio only after a user gesture, so any tap on the page starts it and a notice asks for one while it cannot play. Status tabs share one arrival baseline because the order watermark is restaurant-wide; first load, foreground resume and reconnect establish a silent baseline. Persist only minimal pending action identifiers per tab/restaurant/account, before the POST, but show a marker only once its result is unknown; recovery is GET-only and fresh writes require human confirmation. Cancel late work on lifecycle/identity changes. See `docs/reference/kitchen-pass.md` for contracts and verification entry points.

## Pass Screen Rules

The pass screen (`/staff/pass`) lists READY items whose nullable `ServedAt` is empty, in ACTIVE sessions only, oldest `(ReadyAt, Id)` first, grouped per visit in the UI. Every closure, including VOIDED and NO_SHOW, stamps the visit's remaining unserved READY items at the closing time to remove them from the pass; a closure-stamped `ServedAt` does not prove actual handover to the customer. `MarkServedAtClosure` stamped earlier closed visits, and the partial pass index holds only open visits. There is no SERVED status: status, ProcessedAt, billing counts and cancellation rules ignore `ServedAt`, and closure never requires it. For a delivery order "served" means handed to the rider; the wording is the same in every channel. `POST .../items/{itemId}/served` resolves the item binding, takes only session UPDATE, then a conditional update (`status = 'READY' AND served_at IS NULL`); it never changes BillVersion or the order. Repeats and races return ORDER_ITEM_CHANGED, closed sessions SESSION_CLOSED. The list returns the restaurant-wide `latestReadyAt` watermark, which only a newly ready dish can raise; the chime compares it with a silent baseline like the kitchen's order watermark (`watermarkAdvanced` in `lib/live-view.ts`); serving and closure only lower it. Served writes persist no pending marker: the conditional write makes a repeat harmless and the list itself is the recovery read, so after an unknown result the page refreshes and a human taps again. STAFF reach it from the tabs, after Kitchen, in the slot OWNER uses for Bill; OWNER reaches it from 首页 (`staffManagementItems`); there is no lock, undo, confirmation or served history. See `docs/reference/kitchen-pass.md` for contracts and tablet setup.

## Billing and History Rules

Active bills are STAFF/OWNER readable; PAID closure and full closed history require OWNER. The bills page lists every ACTIVE session in all channels from `GET /api/staff/sessions/active`, which reads only open visits through the partial index `ix_dining_sessions_active`; summaries carry `channel`, `deliveryFeeCents` (delivery only) and, for online orders, `online` with the customer's phone and the delivery address and notes. The bill amount is computed only in `SessionSummaries.Project`: uncancelled items plus the delivery fee while any item is not cancelled, so a fully cancelled delivery is a zero bill that closes as VOIDED and PAID/NO_SHOW record the fee; order amounts never include it. OWNER corrects an ACTIVE delivery's fee with `PATCH /api/owner/sessions/{id}/delivery-fee` (`expectedBillVersion`, `deliveryFeeCents`): session UPDATE only, `BILL_CHANGED` for another version, `SESSION_NOT_DELIVERY` for other channels, a changed fee increments BillVersion and the same fee writes nothing. The bills page edits it inside a `ConfirmDialog` frozen with the bill and persists no marker: the version makes a repeat harmless, every outcome rereads the bill and an unknown result asks the owner to check the current fee. Online sessions close through PAID, NO_SHOW and VOIDED with their own wording (collected or delivered; customer didn't come or delivery refused, `closeLabel`; customer told), and never EMPTY, because acceptance always creates their order. NO_SHOW (`POST /api/owner/sessions/{id}/close-no-show`, OWNER, `noShowConfirmed`) accepts online sessions only (`SESSION_NOT_ONLINE` otherwise), has PAID's conditions (positive receivable, no NEW items, `SESSION_NOT_PAYABLE` for a zero bill) and records the uncollected receivable; the page offers it beside checkout whenever checkout is possible, and history always offers its filter, even after online ordering is turned off. Bill reads hold session SHARE; every closure holds only session UPDATE and never takes restaurant/table row locks afterwards. Recompute the bill amount, item counts and version inside the transaction. Summaries retain orderCount and expose itemCount/newItemCount/cancelledItemCount (lines, not portions). PAID requires positive receivables and no NEW items; VOIDED requires existing orders with every item CANCELLED, zero total and guests-left confirmation. EMPTY remains limited to no orders of any status. Paused entrances do not prevent closure. Persist CLOSED, reason, total, closing time and null code ciphertext atomically without incrementing BillVersion, and in the same transaction mark the visit's unserved READY items served at the closing time. Identical closure type/version/amount on an already closed session returns its stored result; mismatches cannot rewrite it. Clamp closing time to opening, the latest order creation/processing time and the latest existing served time in the same restaurant/visit; preserve recorded served times and automatically stamp the remaining READY lines. Delivery taps remain optional.

Bill orders page ascending by creation time/ID, default 50/max 100; cursors bind tenant, session, active/history mode and bill version. BILL_CHANGED returns currentBill and resets loaded bill pages. History uses stored snapshots/closed totals, exact trimmed case-sensitive historical table labels and closure reasons. Default dates are the restaurant's local today; explicit dates are a paired inclusive range converted to UTC boundaries with DST. History sorts closed time/ID descending; cursors bind tenant and resolved filters, retaining date bounds across midnight.

Keep selected session IDs in URL search. Freeze confirmation version/amount; polling must not silently replace them. Active bill polling is 30 seconds while visible/online; stale, failed and resumed-but-not-refreshed views cannot close, reported through `syncIsStalled` like the kitchen. Persist only session ID/closure kind per tab/account/restaurant; unknown closures recover by GET of the original session, never automatic POST. Clear protected guest state through existing lifecycle checks and invalidate affected private queries after closure. See `docs/reference/billing-history.md` for contracts, experiments and validation.

Lock-screen push (step 8) notifies staff devices of new online requests; it is a reminder only and carries no correctness. `WebPush:PrivateKey` (64 hex characters; the public key is derived from it) and `WebPush:Subject` (`https:` or `mailto:`) turn it on together; both empty turns it off, anything else fails startup. Each device registers with `PUT /api/staff/push/subscription` (STAFF/OWNER, password changed), an upsert on the endpoint that binds it to the signed-in account, its credential version, the sign-in's expiry (`CurrentAccount.TicketExpiresAt`) and the notification language; signing in on the device as another account moves the row. The server POSTs to the endpoint, so only HTTPS endpoints of known browser push services are accepted (`PushEndpoints`). `PushTargets.RemoveLapsedAsync` is the only rule for devices that stop receiving (inactive account, password change required, another credential version, expired sign-in, time from `TimeProvider`) and deletes them before registering, so credential writes never touch push rows. At most 20 receiving devices per restaurant (`PUSH_DEVICE_LIMIT`, a soft cap); `DELETE` removes only the restaurant's own row. Neither write persists a browser pending marker: both are idempotent. In the browser, `StaffLayout` owns one push controller through React Context; the home switch, automatic reconciliation, password changes and logout share its operation tracker and state. The tap requests permission immediately, subscribes and PUTs the device; only a successful PUT for the current identity, endpoint, key and language shows "on". Failed registration retains the browser subscription and exposes retry/turn-off actions. Reconcile at startup, identity/language/password changes, foreground return, focus and reconnect, deduplicating concurrent events and discarding obsolete results. No retry timers, durable markers or service-worker background registration: a rotated subscription is uploaded at the next foreground check, and old endpoints use existing lapsed/404/410 cleanup. Signing out pauses reconciliation, waits for in-flight work and sends the browser endpoint in `POST /api/auth/logout` as optional `pushEndpoint` (nullable, max 2048, unknown fields rejected, `{}` compatible). The server deletes the current restaurant's row before clearing the cookie, including first-password-change and online/push-off accounts. Without the Service Worker API, a staff worker registration or PushManager, logout proceeds without an endpoint. Actual registration/subscription read or deletion failure leaves the user signed in with manual retry/identity recovery; do not silently ignore it. The browser keeps its subscription for the next sign-in. Already-dispatched notifications can still arrive. Only "turn off for this device" removes the browser subscription, after a best-effort DELETE. A subscription made with an older VAPID key is dropped and needs a new tap. Development builds register no worker, so push is unsupported there; iPhone and iPad must install the app first. Opening `/staff/online` closes this device's online-order notifications. Only a committed first submission enqueues a notification (`PushQueue`, after `CommitAsync`); `PushSender`, the only `BackgroundService`, deletes lapsed devices, then sends `{ number, language }` encrypted per device with VAPID, `TTL` until the request expires and high urgency. No customer data, IDs or retries; a 404/410 deletes that device, other failures are only logged. The named push HttpClient removes all default loggers to keep secret endpoint paths out of logs. Never log endpoints, keys or payloads. See `docs/reference/online-ordering.md`.

## Platform Administration

`Platform/` owns the independent Platform cookie, bootstrap/recovery CLI and restaurant/account management. Browser selects Platform for `/api/platform`, Guest for `/api/public`, Store otherwise. Platform has a persistent cookie with a fixed 30-day ticket, no sliding renewal and its own limiter; every request verifies active state and credential version. CSRF additional data binds all tokens, including anonymous tokens, to the three scopes. Platform does not grant store business permissions. Use `CurrentPlatformAccount` only for platform administration and `CurrentAccount` for OWNER staff maintenance.

Create the client-selected restaurant UUID and both store accounts atomically: SUSPENDED, ordering off, EUR/Europe/Rome, first password change required. Generated temporary passwords appear only in the successful create/reset response. Expected target credential versions protect reset/active writes; use ACCOUNT_CHANGED for target conflicts, never the current-user credential error. Suspend locks the restaurant and closes ordering; enabling ordering checks ACTIVE under that same lock. Restoring ACTIVE does not enable ordering.

Permanent deletion (`DELETE /api/platform/restaurants/{id}`) accepts only a SUSPENDED restaurant: one conditional `DELETE ... WHERE service_status = 'SUSPENDED'`, so a concurrent reactivation cannot slip in, and the database's `ON DELETE CASCADE` foreign keys remove every tenant row (photos through their dish); never delete child tables by hand. Active visits and unpaid bills do not block it, because the platform cannot close bills. It returns 204, RESTAURANT_NOT_SUSPENDED (409) or RESTAURANT_NOT_FOUND, which is also what a repeated request gets, and logs the actor and the restaurant name as the only remaining trace. The detail page offers it only while suspended, behind the inline management confirmation listing the consequences and requiring the typed restaurant name. It uses the usual pending marker; recovery treats a 404 for any non-create marker as gone and clears it, so a deleted restaurant never blocks later writes.

Restaurants carry an optional `GoogleMapsUrl`, reserved for a future public restaurant list. It is set at creation or through `PATCH /api/platform/restaurants/{id}/google-maps-url` (blank clears it), which updates only that column. `InputRules.IsGoogleMapsUrl` accepts only HTTPS Google Maps links (`maps.app.goo.gl`, `maps.google.*`, `google.*/maps`) up to 2048 characters, because pages render it as a plain href. Only the platform `RestaurantSummary` returns it and only platform pages show it; store, guest and subscription responses never include it.

Restaurants carry a `Theme` preset (`TERRACOTTA` default, `LACQUER`, `INDIGO`, `INK`, `TARO`), set at creation or through `PATCH /api/platform/restaurants/{id}/theme`, a single-column update without confirmation, like the map link. Unlike the map link, it is returned to the store (`restaurantTheme` on `/api/auth/me`) and to guests (`restaurant.theme` in the public bootstrap); OWNER has no theme write.

The join-code switch follows the map-link pattern: a single-column update that waits for guest joins' restaurant SHARE locks, logs the actor and sends the target value, behind the inline management confirmation.

The platform also sets each restaurant's services and online link (`services`, `slug`), at creation and from the detail page behind the same inline confirmation; the rules are in Online Ordering Rules.

Frontend `features/platform/` uses separate identity, request/CSRF functions and `platform` query keys; `/staff/settings` is OWNER-only. Use direct promises for secret-bearing writes; never cache or persist temporary passwords. Cancel late work and clear secret displays on navigation, identity and visibility changes. Persist only scoped pending identifiers/expected versions before writes. Recover through GET; create retries need explicit confirmation and the original UUID. Reset recovery compares versions but cannot recover a lost password or prove which administrator changed it. Other identities' caches and pending markers must survive unrelated login/logout. See `docs/reference/accounts-platform.md` for contracts and recovery behavior.

## Restaurant Subscription Rules

Platform manages free-text owner contact and the default annual fee. OWNER reads only its restaurant through `GET /api/owner/subscription` and has no subscription writes; STAFF and Guest never receive subscription/contact information. `features/subscriptions/` owns platform period forms, the OWNER `/staff/subscription` page and visible/online 60-second reminders. Private queries include restaurant/account IDs; platform queries retain the `platform` prefix.

Each non-overlapping service period stores inclusive start, exclusive end, agreed years and whole-period EUR integer cents. Nullable `PaidOn` is the only payment-state source; one full collection per period. Collecting money never shifts agreed dates. Renewal adds a period; changing default annual fee never rewrites existing agreements. Paid amount/date are frozen; the dedicated expiry endpoint is the only change a paid period accepts. Service expiry and unpaid periods only warn and never automatically change restaurant service or ordering. Contiguous periods extend the displayed final expiry; gaps retain expired warnings until service resumes. Due reminders begin seven days before the exclusive cutoff; started unpaid periods remain due even after expiry. V1 keeps no change history or owner inbox.

Reads return the summary and every period from one Repeatable Read snapshot, without paging. All subscription writes own a transaction, lock restaurant UPDATE, require the expected subscription version, increment it only when something changed and return the fresh detail. The version is the only duplicate guard: a lost, repeated or late request applies only to the state it was confirmed against. At most one state-changing write consumes a version; unchanged saves do not increment it. Stale versions receive `SUBSCRIPTION_CHANGED`, a target conflict, never an identity failure. Subscription writes are therefore the exception to persisted unknown-result markers: the browser stores nothing, refreshes after an unknown result and requires a fresh human confirmation. Build initial periods/payments in the same transaction as restaurant and accounts. Each applied write logs the platform actor, restaurant and action, never amounts or contact. See `docs/reference/restaurant-subscriptions.md` for contracts and validation.

## Online Ordering Rules

Online ordering was built on `feature/online-ordering` step by step from the design in `docs/online-ordering.md` (Chinese; §12 lists the steps and records where the code differs). Customers order from `/r/{slug}` and follow `/o/{token}`; STAFF and OWNER accept or reject on `/staff/online`, and OWNER closes accepted orders on the bills page. Pickup and delivery (restaurant-run, with the fee entered on acceptance) are complete, and so is lock-screen push (step 8), the last step.

Sessions include dine-in, pickup and delivery: `dining_sessions.channel` is `DINE_IN`, `PICKUP` or `DELIVERY`, fixed at creation; the class and table keep their `DiningSession`/`dining_sessions` names. `ck_session_dine_in` keeps the table label (and, while ACTIVE, the table and join code) on dine-in visits; `ck_session_online` keeps online sessions free of table, label and join code. `delivery_fee_cents` exists only on DELIVERY and is then required; `NO_SHOW` closes online sessions only and `EMPTY` dine-in visits only. Session-derived `tableLabel` fields are therefore nullable on the server. Check constraints pass on NULL, so every comparison on a nullable column also states `IS NOT NULL`.

An online submission is one `online_requests` row with no status column: accepted (`accepted_at`, written with `estimated_at` and `session_id`), rejected (`rejected_at`, optional `reject_reason`), otherwise waiting until `expires_at` (submission + 10 minutes) and expired from that instant. `OnlineRequestState` is the only copy of this rule (`Waiting(restaurantId, now)` for queries over the partial index `ix_online_requests_waiting`, `Phase` in memory); every reader of waiting requests uses it with the time from `TimeProvider` passed in, never SQL `now()`, so expired requests never count. Requests store their lines as a jsonb `OrderLineSnapshot` array, with the order item's snapshot fields and nested options; `OrderLineSnapshot.ToOrderItem` is the only conversion to an order item (QR orders use it too) and `OrderLineSnapshotTests` fails when an order item gains a snapshot field the line lacks. `lines.menuItemId` is not a foreign key, so menu deletion never touches requests. `online_counters` holds each restaurant-day's last number; numbers are unique per restaurant and local business date. Customer contact columns are nullable: each new submission clears its restaurant's name, phone, address and notes submitted more than 30 days earlier, in the submission's own transaction through `ix_online_requests_contact` (no background job; repeats and rejected submissions roll back with it). Without a new successful submission, contact data is not cleared. The maintainer accepts the temporary mismatch with the privacy draft's fixed 30-day deletion promise; resolve it during the pre-release privacy review, not by silently adding a background job. Online tables cascade from the restaurant; the request's session link is the composite `(session_id, restaurant_id)` key.

The platform turns QR dine-in and online ordering on per restaurant: `dine_in_enabled` (default true) and `online_enabled` (default false), with `ck_restaurant_services` keeping at least one on. Creation requires `services: { dineIn, online }`; `PATCH /api/platform/restaurants/{id}/services` sends both target values. It takes restaurant UPDATE and refuses to turn off a service that still has open work (`SERVICE_HAS_OPEN_WORK`, 409): for dine-in, any ACTIVE dine-in session; for online, a waiting request or an ACTIVE pickup/delivery session. The UPDATE waits for the SHARE locks that opening, joining and ordering hold, so no visit starts between the check and the switch. Turning a service on needs no check. `ordering_enabled` (accepting orders) belongs to dine-in only and the switch leaves it untouched.

`slug` is the readable online link `/r/{slug}`: 3–40 lowercase letters, digits and hyphens with no hyphen at either end (`InputRules.IsSlug`, repeated by `ck_restaurant_slug` and the platform form's `isSlug`), globally unique (`uq_restaurant_slug`, `SLUG_CONFLICT` on creation or change) and required while online ordering is on (`ck_restaurant_online_slug`; the services write rejects online without a link). `PATCH .../slug` is a single-column update; it never clears the link, so turning online ordering back on restores it. A change breaks the old link and its printed QR codes at once; table QR codes are unaffected. Both writes log the actor and use the usual management pending marker.

`/api/auth/me` returns `services`; the platform `RestaurantSummary` returns `services` and `slug`. Without dine-in, `DiningEntrance.Require` rejects opening, joining, guest code reads and QR orders with `DINE_IN_NOT_OFFERED` (409, checked after `SERVICE_SUSPENDED`; an order replay still returns first), turning accepting-orders on returns the same code, and the floor read stays available because home notices and the bills page use it. The QR bootstrap returns `dineInEnabled: false` with the full menu, and guests see the same notice as for a suspended restaurant. Platform changes reach store pages at their next identity refresh. See `docs/reference/accounts-platform.md`.

Each restaurant's online settings live on `restaurants` (`public_phone` and delivery set by OWNER, `online_paused_until` set by STAFF or OWNER) and in `online_hours` (OWNER): at most two slots per ISO weekday in local minutes, `opens < closes <= 1440`, never crossing midnight, the second starting no earlier than the first ends; the end is the last moment to order. Saving replaces the whole week. Every settings write takes restaurant UPDATE, refuses a restaurant without online ordering (`ONLINE_NOT_OFFERED`) and returns the fresh settings; none persists a pending marker, because each sends its target. The settings page disables edits and reset during a save, tracks writes with `useOperations` and discards late results after lifecycle or identity changes. A current success cancels older settings reads, caches the returned settings and clears only that save's draft. Failures retain the draft; the existing 60-second poll and ordinary focus/reconnect reads reveal later state, without an extra post-write GET or recovery loop. `OnlineAvailability.Evaluate` is the only "can customers order online now" rule (SUSPENDED → NOT_OFFERED without online or phone → PAUSED → CLOSED_HOURS with `nextOpensAt` → BUSY with 20 waiting requests → OPEN), always with the time from `TimeProvider` passed in, never SQL `now()`; `OnlineAvailability.ReadAsync` loads its hours and waiting count inside the caller's transaction for the settings page, the online menu and submissions. A pause lapses on its own: `SLOT` lasts until the current slot ends (`ONLINE_CLOSED` outside the hours) and `TODAY` until local midnight; resuming clears it. Local times convert through `OnlineSchedule.ToUtc`, which moves a time skipped by DST to the jump and takes the first of a repeated time. Phones use `InputRules.NormalizePhone` (optional `+` and 6–15 digits, whitespace removed). Delivery is `delivery_enabled` (default false) plus an optional note per language (`delivery_note_zh/it/en`, up to 500 characters trimmed, blank stored as NULL) with the area and fee rules; `PUT /api/owner/online/delivery` replaces the switch and the three notes together. Delivery never changes `OnlineAvailability`; turning it off only stops new delivery submissions, so waiting delivery requests can still be decided and accepted ones close as usual, and it keeps the notes. `/staff/online-settings` shows the link and its QR (`publicMenuUrl` accepts `/r/{slug}`; `qrPng` is shared with table QR codes) and rereads every 60 seconds while visible. See `docs/reference/online-ordering.md`.

Customer APIs are anonymous under `/api/public` (`OnlineOrderController`, `[AllowAnonymous]` together with `[Authorize(Policy = GuestAuthentication.Policy)]`, so the Guest identity, never the Store fallback, authenticates and binds the public CSRF token even when the browser also holds a store cookie): the menu `GET /r/{slug}/bootstrap` (one Repeatable Read snapshot, the full menu in every status, `ONLINE_LINK_NOT_FOUND` for unknown slugs), the submission `POST /r/{slug}/requests` (CSRF from `/api/public/csrf`), recovery `GET /r/{slug}/requests/by-client-id/{id}` and the status page `GET /online-orders/{token}`. A submission validates its format first, then locks restaurant SHARE (rechecking the slug) → the restaurant's transaction advisory submission lock (`hashtextextended` of the fixed `tavoloflow:online-submission:` prefix and restaurant ID) → reads time and business date → the day's `online_counters` row through `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` → returns an existing `(restaurant, clientRequestId)` result and rolls back, before any service, hours, cap or menu gate → requires `OPEN` (`SERVICE_SUSPENDED`, `ONLINE_NOT_OFFERED`, `ONLINE_PAUSED`, `ONLINE_CLOSED` with `nextOpensAt`, `ONLINE_BUSY`) → refuses delivery while the restaurant's delivery switch is off (`DELIVERY_NOT_OFFERED`; pickup never depends on it) → snapshots lines through the shared `OrderLines` check (`MENU_CHANGED`) → inserts with a random 32-byte status token and `expires_at` ten minutes later. 201 first, 200 for a repeat with the same `{ statusToken, number, expiresAt }`; any rejection rolls back, so numbers have no gaps. The submission lock serializes all submissions of the same restaurant across business dates, so duplicate and 20-request cap checks cannot race at midnight; other restaurants proceed independently. This order is part of the global lock order alongside restaurant → table → session, restaurant → menu item and restaurant → online request. Business dates are the restaurant's local date at the time read after acquiring the submission lock. Submissions are limited per IP (`OnlineRateLimiter`, 10 per 10 minutes). Recovery uses the random client request ID as its credential and 404 (`ONLINE_REQUEST_NOT_FOUND`) only means not found yet. The status page returns the phase from `OnlineRequestState`, the submitted snapshot before acceptance and the order items with the session's bill amount after; it never returns the customer's phone, an address or any request or session ID, and returns `ONLINE_ORDER_NOT_FOUND` from 24 hours after the order ended (expiry, rejection or the accepted session's closure: `OnlineRequestState.EndedAt`). Never log request bodies, names or phones.

The customer pages are anonymous: reads use `publicRequest`, the submission `publicWrite` (public CSRF token, same-origin credentials for the antiforgery cookie), and query keys keep the `public` prefix (`["public", "online", slug]` every 30 seconds, `["public", "online-order", token]` every 10 seconds while visible and online until the order ends). They share the QR menu's language memory per restaurant (the status response carries the restaurant `id`) and its menu, option picker, cart bar and cart lines, whose props accept any cart with `{ lines, pending }`. The online cart is tab-scoped (`tavoloflow:cart:{restaurantId}:online`, version 1) with the QR limits. "Checkout" rereads the bootstrap, requires `OPEN` and refreshes prices before the confirmation form (name and phone, the as-soon-as-possible note and a privacy line; with delivery on, a pickup/delivery choice, and for delivery the address (1–200), optional doorbell/floor notes (up to 100), the restaurant's note in the customer's language and "the restaurant confirms the fee"). A delivery choice falls back to pickup, with a notice, when that reread finds delivery off; the intent carries the fulfillment, address and notes (null for pickup); placing the order persists and reads back the full intent before the POST, and blocked storage prevents sending. Success clears the cart, remembers the status token per restaurant in `localStorage` (`tavoloflow:online-order:{restaurantId}`, cleared once the order ends) and opens `/o/{token}`. Any understood rejection of a first attempt frees the cart; after an unknown result the page recovers by GET on mount and every 30 seconds, never by POST, and offers a manual retry of the identical saved request. Unlike QR ordering, a retry rejected with a code the server returns only after its duplicate check (service, link-off, pause, hours, busy, delivery and `MENU_CHANGED` gates, all inside the transaction holding the restaurant's cross-day submission lock and the day's counter row) frees the intent, because it proves no request with that ID was stored; any other rejection after an unknown result keeps it (`submissionFailure`). Every failure notice offers the restaurant's phone. The status page derives its wording from the phase, session status, close reason and dish statuses in `state.ts` (`orderView`, `statusCopy`) and puts the phone first when the order did not go ahead; customers cannot cancel. The privacy page text is a draft to be reviewed before release.

Staff decide on waiting requests (`OnlineStaffService`). `GET /api/staff/online/pending` returns every waiting request through `OnlineRequestState.Waiting` (no paging or limit: the cap and the ten-minute window bound it) with the server's `now`; `GET /api/staff/online/active` returns accepted orders whose session is ACTIVE, through `ix_dining_sessions_active`, built from their bill summaries so the amount to collect (`totalAmountCents`, with `deliveryFeeCents`) is the bill's own. Acceptance locks restaurant SHARE → the request row UPDATE (`RowLocks.OnlineRequestAsync`; global order restaurant → online request), requires the request still waiting at the current time (`ONLINE_REQUEST_CHANGED` otherwise), refuses a SUSPENDED restaurant (`SERVICE_SUSPENDED`) but ignores pause, hours, sold-out and delivery switches, takes `estimatedMinutes` from the request's choices (pickup 10/20/30/45, delivery 30/45/60/90), requires for delivery a `deliveryFeeCents` entered by whoever accepts (0 when free, items plus fee a safe integer) and none for pickup, checks which dishes still exist under the restaurant lock, and in one transaction creates the ACTIVE `PICKUP` or `DELIVERY` session (bill version 1, the fee on delivery), its single order (`created_at` = acceptance time, the request's client request ID, total and language) and the items through `OrderLineSnapshot.ToOrderItem`, then sets `accepted_at`, `estimated_at` and `session_id`. Rejection owns a transaction and locks only the request row UPDATE, then reads time from `TimeProvider`, checks `OnlineRequestState.Phase` and conditionally updates the still-waiting request with an optional reason (`OUT_OF_RANGE` only for delivery). Waiting past expiry returns `ONLINE_REQUEST_CHANGED`; it never backdates a rejection. Neither write persists a browser pending marker: both apply only to a waiting request, so a repeat gets `ONLINE_REQUEST_CHANGED`, and the refreshed list shows what a lost write did. With online ordering on, `StaffLayout` mounts `OnlinePendingBanner` for signed-in staff: it polls the pending list every 10 seconds while visible and online (store key `online-pending`, shared with `/staff/online`), shows one sticky line while requests wait (a warning at the cap) and rings `onlineRing` every 3 seconds while someone waits and the shared `syncIsFresh` rule passes: a successful read under 30 seconds old, no failed read, visible and online, and refreshed since resume. Cached counts remain visible without an additional stale banner state; stale data never authorizes decisions on the orders page. It has no mute, stays mounted at zero so the first tap unlocks audio, and asks for that tap while audio is blocked. `/staff/online` accepts a pickup with one tap on a time and a delivery once its fee is typed (showing subtotal + fee = total; the address is a plain Google Maps search link), rejects behind `ConfirmDialog` with an optional reason (out of range for delivery only), blocks writes while the list is not fresh, rereads the pending, active, kitchen, pass and bills views after every outcome, and lists accepted orders in progress read-only with the amount to collect and the address: the only place STAFF see an accepted customer's phone and address.
