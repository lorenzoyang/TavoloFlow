@AGENTS.md

AGENTS.md (imported above) is the authoritative source for layout, style and the per-area domain rules (lock order, state gates, recovery, limits). Put new domain rules there, not here. This file adds commands and the cross-cutting architecture that AGENTS.md assumes. The root README is English, with Italian and Chinese versions (`README.it.md`, `README.zh-CN.md`) kept in step with it; the frontend README and the reference docs in `docs/reference/` (product requirements, feature contracts, schema) are written in English only; `docs/README.md` indexes them alongside the user's personal development, self-hosting, local-development and learning guides, written in Italian under `docs/it/` and translated under `docs/zh-CN/` and `docs/en/` with the same filenames. Temporary maintainer notes are not additional specifications. Backend error messages are English, for developers; pages translate the error code in every language. Store pages (OWNER and STAFF, `/staff`) and platform pages (`/platform`) have zh/it/en copy chosen per device (AGENTS.md “Interface language”). Guest-facing copy (`public-menu`, `guests`, `orders`) also has zh/it/en variants, chosen per guest.

## Commands not covered in AGENTS.md

Backend (repository root):

- One-time setup: `dotnet tool restore` (pins `dotnet-ef` and `csharpier`). Then `dotnet user-secrets set 'ConnectionStrings:Default' '<conn>' --project backend/TavoloFlow.Api` and `dotnet ef database update --project backend/TavoloFlow.Api`. Compose does not configure the API connection string.
- Single test class or method: `dotnet test TavoloFlow.slnx --filter "FullyQualifiedName~KitchenTests"` (append `.MethodName` for one test). Each test class takes its own `IClassFixture<PostgreSqlFixture>` and starts its own `postgres:18-alpine` container, so Docker must be running.
- Schema change: `dotnet ef migrations add <Name> --project backend/TavoloFlow.Api --output-dir Data/Migrations`, then check with `dotnet ef migrations has-pending-model-changes --project backend/TavoloFlow.Api`. Migrations are forward-only and never run at startup. Deployment applies them explicitly with the EF migrations bundle (`efbundle`) that `deploy/Dockerfile.api` builds into the API image and `deploy/install-release.sh` runs after its backup and before starting the new API. See `docs/it/local-development.md` for schema tooling and `docs/it/self-hosting.md` for deployment migrations.
- `Program.cs` also acts as a one-shot CLI (`Operations/MaintenanceCommands.cs`). Pass exactly one of `--seed-dev-accounts`, `--seed-platform-admin`, `--reset-platform-password` or the Development-only `--seed-demo`; it runs the command and exits without serving.

Frontend (`frontend/`):

- Single test file: `node --test --test-isolation=none tests/orders.test.ts`. Add `--test-name-pattern "<regex>"` to run one test.
- Node runs these tests by stripping types directly from `src/`. Modules covered by `tests/*.test.ts` (feature `state.ts`, `public-menu/language.ts`, `qr-url.ts`, `response.ts`, and `lib/format.ts`, `lib/ids.ts`, `lib/language.ts`, `lib/live-view.ts`, `lib/operations.ts`, `lib/query-scope.ts`, `lib/staff-language.ts`, `lib/theme.ts`) therefore use relative imports with explicit `.ts` extensions instead of `@/`. They may only `import type` from modules that use `@/` or browser/React APIs. Keep logic you want to test in these pure modules.

## Backend architecture

- **Request flow.** Controllers are thin. Each one declares an `[Authorize(Policy = ...)]` and calls a scoped service with the restaurant ID taken from `CurrentAccount.RequireUser()`. Services reject requests by throwing `ApiException`, usually through a module factory (`DiningErrors.SessionClosed()`, `BillingErrors.Changed(bill)`). The globally registered `ApiExceptionFilter` (`Common/ApiErrors.cs`) turns it into the shared `ApiError` body `{ code, message, requestId, errors, ...extensions }`; extensions carry `currentBill` and `changes`. Each module keeps its DTOs and error factories in `<Module>Contracts.cs`.
- **Authentication.** `Common/BrowserSecurity.cs` registers the default scheme `Browser`, which forwards by path: `/api/platform` goes to Platform, `/api/public` to Guest, and everything else to Store. The same path mapping scopes CSRF tokens (`BrowserCsrfScope`). Each identity module (`AddStoreAccounts`, `AddGuestAccess`, `AddPlatformAccounts`) only adds its own cookie scheme and policies. The default and fallback authorization policy is Store Staff (OWNER/STAFF with the password already changed), so new endpoints are protected unless they opt out explicitly. `CsrfValidationFilter` is registered globally on controllers. Trusted identity comes from `CurrentAccount`, `GuestIdentity` or `CurrentPlatformAccount`, never from request bodies.
- **Concurrency.** Services own their transactions. Row locks are taken with raw `SELECT ... FOR SHARE/FOR UPDATE` via `Data/RowLocks.cs` (`RowLock.Share`/`RowLock.Update`; global order: restaurant → table → session, and restaurant → menu item), with `AsNoTracking`, followed by conditional updates. `Dining/DiningEntrance.cs` SHARE-locks a guest entrance (restaurant + table) and applies the entrance rule. `DiningSession.BillVersion` is the optimistic version that clients send back when closing a bill. Tables are snake_case, mapped explicitly in `Data/Configurations/`, and enums are stored uppercase via `UppercaseEnumConverter`.
- **Time.** Code reads time from an injected `TimeProvider`, never from `DateTime.UtcNow`. Tests replace it with `TestClock` to advance cookie and ticket lifetimes.
- **Integration tests.** `AccountTestHost` (`WebApplicationFactory<Program>`) points the app at the fixture's database and swaps in `TestClock`. It can lower rate limits (`lowLimits`) or run as Production. `Browser()` returns an HTTPS cookie-holding client, `PostAsync` fetches a CSRF token automatically, and `AssertErrorAsync(response, status, code)` checks error codes. Race tests block a transaction at a precise point with `DbCommandInterceptor` subclasses (see `LockGate` in `KitchenTests.cs`).

## Frontend architecture

- **Four request identities** live in `src/lib/api.ts`: store (`request`/`write`), anonymous (`publicRequest`), guest (`guestRequest`/`guestWrite`) and platform (`platformRequest`/`platformWrite`). Each write first fetches a fresh CSRF token from its own scope's endpoint. A store 401 or `CREDENTIALS_CHANGED` triggers the global handler that `main.tsx` registers via `setAuthFailureHandler`; platform failures have their own handler. Writes whose result may be lost use `withTimeout(signal)`.
- **Query-key scoping.** The first query-key segment decides which identity owns cached data: `public`, `guest`, `platform`, `["auth","me"]`, or anything else, which counts as store-private. `src/lib/query-scope.ts` uses these predicates to cancel and clear only the affected caches on login, logout or identity change; a store identity change also clears the mutation cache, whose variables can hold passwords. Choose the prefix deliberately for every new query and build keys with the feature's key factory. Store keys that other pages refresh after a service write are `[view, restaurantId, userId]` from `storeKey` in `lib/store-views.ts`; other features call `invalidateStoreViews(client, account, [...views])` instead of importing those factories.
- **Feature module shape.** `api.ts` holds every request function, query key factory and response type of the feature; components and hooks never build API paths themselves (the node-tested recovery helpers `closureRequest`/`recoveryPath`/`recoveryUrl` in `state.ts` are the deliberate exception). Writes take a request thunk, for example `mutation.mutate(() => saveItem(id, body))` or `run(intent, signal => createRestaurant(input, signal))`. Shared helpers live in `lib/` (`format.ts`, `ids.ts`, `language.ts`, `live-view.ts`, `useLiveView.ts`, `query-client.ts`, `operations.ts`/`useOperations.ts`, `usePendingMarkers.ts`, `store-views.ts`). `state.ts` holds pure, node-tested logic: validation, cart/intent rules, recovery parsing. `use<Feature>.ts` hooks handle polling, visibility/online gating and abortable late-response handling. `*Page.tsx`/`*Views.tsx` render. Guest, store and platform copy always lives in the feature's `messages.ts` (one object per language typed as the Chinese one, `Record<Language, typeof zh>`, so a missing translation fails `tsc`); components never inline user-facing text.
- **Unknown-result writes.** Before a POST whose result may be lost, the hooks persist minimal tab-scoped identifiers to `sessionStorage`. They recover only by GET of the original resource. Every hook tracks its requests with `useOperations` (`lib/operations.ts`): `op.isCurrent()` tells a late result whether it still applies, a lifecycle change calls `cancelAll()`, unmounting cancels everything, and `invalidate()` discards results without aborting (the guest page hides its join code this way). Kitchen and billing keep their list of markers with `usePendingMarkers`, which also schedules their GET recovery; the floor, cart and platform management keep their own single marker. There are three exceptions: manual order retry resends the same ID and body; platform subscription writes persist nothing because their expected version already lets each confirmed write apply at most once; and pass-screen served writes persist nothing because they only apply to a READY item not yet served, and the refreshed pass list shows whether a lost write went through.
- **UI layer.** Pages compose the shared pieces in `src/components/` (rules in AGENTS.md “UI Conventions”). `StaffLayout` observes the identity query: it shows only the brand until the account is signed in with a changed password, then renders `StaffNav` (bottom tabs on phones, side rail from `md`) from the single list in `features/accounts/navigation.ts`. It also makes the staff area installable: `useInstallableStaffApp` (`features/accounts/useInstallApp.ts`) links the manifest and registers the service worker. Detail views and the guest cart pick an inline column or a sheet with `useMediaQuery(WIDE_SCREEN)` and render their content once, so ids stay unique.
- **Routing.** `routes/staff.tsx` and `routes/platform.tsx` are layout routes wrapping their child pages. `/q/$token` is the guest entry point and sits outside both. `routeTree.gen.ts` is regenerated by `vite build`/`vite dev`.
