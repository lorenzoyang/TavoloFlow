# 第八阶段：平台管理

后续新增的餐厅联系方式、收费周期和线下年费见 [收费周期](restaurant-subscriptions.md)。当前数据库共十一张表，含收费周期和菜品图片。

平台全部页面支持中文、意大利语、英语，切换入口始终位于页头，包括登录和改密页。
平台与店铺共用本设备的语言偏好；有效保存值优先，否则跟随浏览器语言，无匹配时使用英语，退出后保留。
餐厅管理、主题名称及说明、账号操作、临时密码提示和确认区域均随语言切换；建店仍用浏览器原生确认框，其他管理确认保留页内区域。
业务文案在 `features/platform/messages.ts`，共用账号操作文案在 `management-messages.ts`，
`TemporaryPasswords`、`AccountActions` 自行读取当前界面语言。错误按 `code` 翻译，完整约定见仓库根目录 [`AGENTS.md`](../AGENTS.md#ui-conventions) 的 “UI Conventions”。

## 第一步：平台初始化与身份

平台是独立于店铺和顾客的身份。先显式迁移数据库，再通过本地 user-secrets 或环境变量设置
`PlatformBootstrap:Username`、`PlatformBootstrap:Password`（6–128 字符，允许六位纯数字，不能全部为空白）。
执行 `dotnet run --project backend/TavoloFlow.Api --launch-profile http -- --seed-platform-admin`。
它只创建首个平台管理员，完成后退出；再次执行不会覆盖密码或改变启用状态。
恢复密码使用单独的 `--reset-platform-password`，必须匹配已有用户名；这会使旧票据失效，但不会启用已禁用账号。
两条命令可在生产使用，不提供匿名 HTTP 初始化入口。密码配置不写入 Git、不放命令行参数。

从 `/platform/login` 登录。请求链路为：表单 → 平台 CSRF → 登录接口 → PasswordHasher → Platform Cookie。
平台与 Store 均使用固定 30 天的持久 Cookie，关闭浏览器后保留登录，不滑动续期；Guest 仍使用固定 12 小时的浏览器会话 Cookie。
已有票据按原签发期限到期，重新登录或成功改密后签发新的 30 天票据。
每次平台请求检查当前数据库状态和凭据版本；平台身份不具有店铺账单权限。
三个入口共享 CSRF 设施，但 token 额外绑定 store/platform/guest 用途，即使尚未登录也不能混用。

练习：在同一浏览器分别登录店铺和平台，检查 Network 中的 `/me` 和 Cookie Path；
在第二浏览器登录平台，然后从第一浏览器改密，观察第二浏览器下次请求被拒绝。
阅读 `PlatformAuthentication`、`PlatformAccountService`、`PlatformAuthController`，区分认证、权限和凭据失效。

## 第二步：建店、服务启停与账号恢复

平台餐厅列表支持名称包含筛选、ACTIVE/SUSPENDED 筛选和页码分页（每页默认 20，最多 100）。
创建餐厅要求名称、默认菜单语言及两个不同的登录名。客户端发送创建前保存的餐厅 UUID；
数据库把餐厅和 OWNER/STAFF 放在一个事务中创建。用户名冲突不会留下半家餐厅。
EUR/Europe/Rome 为本版创建默认值，默认语言后续仍由 OWNER 的既有设置接口管理。

餐厅可以登记一个 Google 地图链接，为以后官网列出使用本服务的餐厅预留。只接受 HTTPS 的 Google 地图链接
（`maps.app.goo.gl`、`maps.google.*` 或 `google.*/maps`，最多 2048 字）：建店时填写，或在餐厅详情页单独编辑，留空保存即清除。
单独编辑只更新这一列，不改变收费版本。链接只出现在平台接口和平台页面，店铺、顾客和收费接口都不返回。

建店时可选择是否需要入桌码（`joinCodeRequired`，默认 true）。之后在餐厅详情页经内联确认后，
通过 `PATCH /api/platform/restaurants/{id}/join-code-required`（`{ "joinCodeRequired": false }`）切换。
接口发送目标值而不是取反，所以迟到或重复的请求只会留下所选的值。它只更新这一列，并记录平台操作者。
切换对正在用餐的桌位立即生效；重新开启时，已加入的顾客授权保留。规则见[开桌与顾客授权](dining-guest-access.md)。

每家餐厅有一个配色主题（`theme`），建店时选择，之后在餐厅详情页「更换主题」，通过
`PATCH /api/platform/restaurants/{id}/theme`（`{ "theme": "INK" }`）修改。可选值固定为五个预设，按颜色命名，
提示只是建议的餐厅类型：`TERRACOTTA` 赤陶（默认，意式、综合）、`LACQUER` 朱漆（中餐）、`INDIGO` 靛蓝（日料、海鲜）、
`INK` 墨黑（拉面、居酒屋）、`TARO` 芋泥紫（奶茶、甜品）。不提供自定义颜色，避免出现看不清的配色。
主题只是颜色，不影响下单、结账等任何规则，所以与地图链接一样只更新这一列、记录操作者，不需要内联确认；
接口发送目标值，重复请求无害。老板没有修改接口。

主题只替换品牌色：背景、文字、主按钮、强调色和边框（`index.css` 的 `[data-theme]` 块），不改布局、字体和圆角。
表示状态的颜色在所有主题中保持不变：黄色是等待或新单，绿色是已出餐或已付，红色是取消或删除。
`frontend/tests/theme.test.ts` 检查每个主题的文字对比度达到 WCAG AA（4.5:1），检查主题块没有改写状态色，
并检查每个主色与状态色的距离不小于默认赤陶与番茄红的距离。新增主题时先通过这个测试。

主题出现在顾客菜单（public bootstrap 的 `restaurant.theme`）和登录后的店铺页面（`/api/auth/me` 的
`restaurantTheme`）。`useDocumentTheme` 把它设在 `<html data-theme>` 上，因为弹窗、下拉菜单和购物车面板通过
portal 渲染在 `<body>` 下，设在页面容器上会漏掉它们。店铺登录、首次改密页面、二维码无效或加载中的顾客页面，
以及整个平台管理端，都保持默认配色。顾客菜单每 30 秒刷新时应用新主题；店铺页面在重新打开或切回前台时更新。

临时密码由服务器生成，仅在建店/重置成功时返回一次。查询只返回账号状态及供并发检查的凭据版本。
前端直接调用写接口，把秘密仅留在当次组件内存；不用 Query/Mutation 缓存存储密码。
隐藏页面、离开页面、改变身份或关闭展示后清除。复制内容的剪贴板由操作者负责及时清理。

服务停用在餐厅行锁内关闭接单，与开桌和下单协调。恢复 ACTIVE 不自动开启接单。
服务停用不禁用账号，不关闭用餐，厨房和结账仍可继续。OWNER 可在 `/staff/settings` 重置本店 STAFF。
重置不改变账号启用状态；禁用或重新启用账号会在实际变更时增加凭据版本，使旧票据失效。

永久删除餐厅：`DELETE /api/platform/restaurants/{id}`，只接受已停用（SUSPENDED）的餐厅，成功返回 204。
服务端只发一条带条件的删除语句（`WHERE service_status = 'SUSPENDED'`），状态检查和删除不会被并发的“启用服务”隔开；
账号、桌台、菜单与照片、就餐、订单和服务期由数据库外键级联删除，不需要逐表删除。
未停用返回 409 `RESTAURANT_NOT_SUSPENDED`；餐厅不存在返回 404 `RESTAURANT_NOT_FOUND`，重复或迟到的请求也得到 404。
进行中的就餐和未结账单不阻止删除，因为平台无法替店铺结账；确认文案会写明它们一并删除。
日志记录操作人、餐厅 ID 和名称，这是删除后唯一的痕迹。
餐厅详情页只在停用后提供删除入口，内联确认列出后果，并要求输入餐厅名称后才能确认。
被删餐厅已登录的店铺设备在下一次请求时退出，顾客的入桌授权同样失效，扫桌码看到二维码无效。
数据会在之后 7 天内的每日备份中残留；恢复备份会回滚整个数据库，所以删除应视为不可撤销。
删除沿用平台写操作的待确认标记：结果未知时 GET 详情，404 即已删除并清除标记。
任何非建店标记在恢复时遇到 404，都表示目标已不存在，同样清除标记，避免已删除的餐厅卡住后续写操作。

未知结果只 GET 核对。建店未查到时不能证明旧请求不会到达，人工再次创建必须使用原餐厅 UUID。
账号重置的迟到请求受预期凭据版本保护，不能覆盖较新凭据。
核对后若无法取得临时密码，必须再次人工确认重置；不会从数据库恢复明文密码。
管理界面使用 `ACCOUNT_CHANGED` 表示目标账号冲突，不会把当前 OWNER/平台管理员误退出。

练习：创建两家店，在店 A 的 OWNER 页面尝试指定店 B 员工；观察接口拒绝额外字段。
分别在两个平台窗口重置同一账号，观察过时版本被拒绝。
拦截建店/重置成功响应，再刷新页面，观察 Network 只有 GET 恢复。

建议按两步阅读各自改动，每步先画出身份与请求链路，再运行一项手动实验。重点理解：为何“恢复餐厅服务”不自动接单，以及为什么凭据版本不能证明哪次未知请求成功。
