# 传菜屏：已出餐、待送到桌的菜品

厨房在厨房页点「出餐完成」后，菜品出现在传菜屏 `/staff/pass`。传菜屏放在出餐口的平板上，按桌显示，
服务员取走菜品时点「已送达」，菜品随即消失。它只解决“哪道菜该送去哪桌”，不影响账单、结账或厨房状态。

## 状态与页面

- 不新增明细状态。`order_items.served_at` 为空表示待送；只有 `READY` 的明细能写入，且不早于 `ready_at`
  （约束 `ck_order_item_served`）。取消和出餐规则不变，结账也不要求菜品已送达。
- 列表只含正在用餐（ACTIVE）的桌。结账时菜品必然已经上桌，所以结账把未点「已送达」的菜品补记为结账时间送达：
  它们随该桌一起消失，也离开待送部分索引，索引只保留正在用餐的菜品，不随历史堆积。
- 每桌一张卡片，桌号大字显示；最早出餐的桌在前，卡内按出餐顺序。每道菜显示名称、数量、备注和已等待时间，
  等待满 5 分钟用 warning 色标出（仅显示，不改变顺序）。
- STAFF 没有账单页，传菜屏占用那个底部标签位置（首页 · 大厅 · 厨房 · 传菜 · 菜单）；OWNER 的这个位置是账单，所以从首页的管理入口进入传菜屏。
- 不做锁屏、撤销、二次确认或“最近已送达”列表；误点的后果只是菜品从屏上消失，由服务员现场处理。

## 接口契约

使用店铺 Cookie、首次改密策略和可信 `CurrentAccount.RestaurantId`；写操作验证店铺 CSRF。

| 方法与路径 | 输入 | 结果 |
|---|---|---|
| `GET /api/staff/pass` | cursor；limit 默认 50/max 100（页面用 100） | `{ items, nextCursor, totalCount, latestReadyAt }` |
| `POST /api/staff/orders/{id}/items/{itemId}/served` | `{}` | READY 且未送达 → 写入 `servedAt`，返回该菜品 |

- 列表按 `(ready_at, id)` 升序 keyset 分页，游标绑定餐厅。菜品、`totalCount` 与 `latestReadyAt` 来自同一个 Repeatable Read 快照。
- `latestReadyAt` 是全店待送菜品中最新的出餐时间。新出餐的菜一定比所有待送菜品更新，所以它只在有菜出餐时前进；
  送达与结账只会让它后退。前端据此响铃，而不是比较已加载的分页。
- 写入先按餐厅、订单、明细绑定找到用餐，再锁 Session UPDATE（与出餐、取消、结账相同），然后执行带
  `status = 'READY' AND served_at IS NULL` 的条件 UPDATE。不改 BillVersion，也不改订单状态。
- 不存在、跨店或错误绑定返回 `404 ORDER_ITEM_NOT_FOUND`；未出餐、已取消、已送达或并发竞争失败返回
  `409 ORDER_ITEM_CHANGED`；已结账返回 `409 SESSION_CLOSED`。
- 列表与写入结果都不含价格、入桌码或客户端请求 ID。

## 前端同步

- 可见且在线时每 10 秒刷新；陈旧、失败、离线或恢复前台后未重新同步时禁用「已送达」，判断与厨房相同（`syncIsFresh`/`syncIsStalled`）。
- **不持久化待确认标记**，这是有意的例外：写入是条件式的，重复提交只会得到 `ORDER_ITEM_CHANGED`，
  而列表本身就能回答一次丢失的请求是否成功。结果未知时提示并刷新列表，菜品仍在则由服务员再点一次。
- 声音默认开启，规则与厨房相同（`lib/useAlertSound.ts`）：需要手势解锁；首次加载、回前台、重连建立静默基线。
  传菜屏是三声短促高音，厨房是两声上行音，两台平板放在一起也能分辨。声音开关与屏幕常亮只保存为设备偏好。
- 厨房出餐或取消后会让传菜屏查询失效，同一设备上切换页面时立即看到最新菜品。

## 平板设置

1. 在出餐口平板上按 [PWA 指南](pwa.md) 安装店铺端，用员工账号登录，在首页点「传菜」。
2. 打开「屏幕常亮」，并把平板的系统音量调高：网页提醒声的音量不会超过设备音量。
3. 锁定在这个页面，防止误触其他页面：
   - iPad：设置 → 辅助功能 → 引导式访问，打开后在传菜页连按三次侧边按钮开始；可以圈出底部导航栏禁止触摸。
   - Android：设置 → 安全 → 屏幕固定（不同品牌名称略有不同），在最近任务中固定 TavoloFlow。
4. 已安装的应用重新打开时回到首页（启动地址固定为 `/staff`），再点一次「传菜」即可。

## 数据升级

`AddOrderItemServedAt` 迁移新增可空列、部分索引 `(restaurant_id, ready_at, id) WHERE status = 'READY' AND served_at IS NULL`
和约束，并把迁移前所有 READY 明细的 `served_at` 设为其 `ready_at`：这些菜品在传菜屏出现之前已经送出，
不能在上线后一次涌入列表。与其他迁移一样通过显式 migration bundle 执行。

`MarkServedAtClosure` 迁移把结账补记规则应用到已关闭的用餐：其中仍为 READY 且未送达的明细，`served_at`
设为该用餐的 `closed_at`（不早于 `ready_at`）。它只改数据，回滚迁移不会还原。

## 验证

后端 `KitchenTests` 中的 `Pass_*` 与 `Served_*` 覆盖：只列出 READY 未送达且用餐中的菜品、分页与游标绑定、
送达只成功一次、BillVersion 与厨房状态不变、租户/CSRF/匿名、结账补记送达时间（已送达的保留原时间）与之后的拒绝、约束和双设备并发。
前端 `tests/pass.test.ts` 验证按桌分组、响铃基线和等待显示。

人工验收：顾客下单 → 厨房点「出餐完成」→ 传菜屏 10 秒内出现并响三声 → 点「已送达」后消失；
结账后未送达的菜品也消失，数据库中其 `served_at` 等于关闭时间；两台设备同时点同一道菜只成功一次。
