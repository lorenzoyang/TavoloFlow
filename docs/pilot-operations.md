# TavoloFlow 试运营手册

部署、备份命令见 [部署说明](../deploy/README.md)，开发学习与实际验证结果见 [第八阶段](platform-pilot.md)。系统只记录已在线下收款的确认，不处理线上支付，也不代替收银/税务系统。

## 开第一家店

1. 平台管理员登录 `/platform/login`，创建餐厅，填写默认语言和全局唯一的 OWNER/STAFF 登录名。
2. 在本次密码展示中复制并安全交付，确认接收人后关闭；不要通过公共群、截图或项目文档交付。关闭后无法再次查询密码，丢失时重新重置。
3. OWNER/STAFF 分别从 `/staff/login` 登录并首次改密。OWNER 配置分类、菜品、价格、三语名称及过敏原，确认可售状态；配置桌位并打印固定二维码。
4. 平台确认配置后启用餐厅服务。店铺手动开启接单；开桌、扫码验证、试下一单、厨房完成，再核对线下收款并清桌。
5. OWNER 检查历史金额及桌号，再开始接待真实顾客。平台管理员不代登录、不查看订单或入桌码。

## 每日操作

开店：检查网络和 `/api/health/ready`，登录账号，核对菜单/供应状态、桌位与遗留用餐，再开启接单。员工开桌后只向本轮顾客告知入桌码。

闭店：关闭接单；继续处理已有厨房订单，核对所有活动账单。正金额、无 NEW 订单才能确认 PAID；全部取消用 VOIDED；没有任何订单才用 EMPTY。不能为关桌而伪造已收款。确认备份完成并记录异常。

平台停用服务会同时关闭接单，保留账号、菜单、活动用餐和订单；恢复服务不会自动恢复接单。账号禁用和服务停用是两个操作，界面会分别显示影响。

## 账号维护

OWNER 可在 `/staff/settings` 重置本店 STAFF。平台在餐厅详情重置 OWNER/STAFF，或禁用/启用账号；重置不会自动启用禁用账号。变更凭据后旧登录失效，员工须用本次临时密码重新登录并改密。

多人同时操作出现 `ACCOUNT_CHANGED` 时，刷新目标账号状态后重新核对；不要反复点击。平台管理员忘记密码时，由拥有服务器秘密配置权限的运维人员执行显式 CLI 恢复；不提供匿名找回或公共注册。

## 断网和未知结果

页面显示“结果待确认”时，先恢复网络并查询原资源。建店使用原餐厅编号；重置只能核对凭据版本是否变化，查不到已经生成的临时密码。版本变化也可能来自另一名管理员，不能据此断言本次请求成功。必须再次核对并人工确认才能发起新写入。

店铺开桌、厨房和关桌同样只通过 GET 恢复；顾客下单有自己的原请求标识，可显式重试原单。不要为了绕过待确认提示而清浏览器数据、开新店或重复收款。存储不可用时管理写入被阻止；保留现场编号并联系负责人核对。

页面身份改变会取消当前身份的请求和显示，其他身份的缓存不被清除。未知操作的最小标识按账号/店铺保存在当前标签页，原账号重新登录后可以核对；它们不含密码。共享设备退出所有使用过的身份，不要只退出平台就交给他人。

## 备份与故障恢复

备份同时包含订单数据与能解密入桌码的密钥，按敏感凭据管理。每日核对成功时间、校验清单与离机副本；按约定定期恢复到新隔离项目。发生故障先停止新增接单，保留线下订单/收款记录，不直接覆盖生产数据库。

恢复脚本会暂停全部餐厅并撤销旧 Store/Platform 票据；旧密码哈希和 Guest 授权仍须人工检查。比较备份后的线下收款、活动账单和账号变更，处理旧活动用餐及凭据后才批准切换。恢复目标先维持隔离，确认 HTTPS、密钥、数据和账号边界，再由店铺手动恢复接单。
